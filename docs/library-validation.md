## 対象と結論

製品ソースは`054b09da130405dafc1f76be3e03bd49e8b80941`、検証driverは`9e19e41e3d32610885bd26ebbecb422c61e3a222`。後者は製品ソースを変更せず、Simulatorのプロセス監視を定義する。文書のみの更新後も、各runと対象コミットの入力hashを照合する。

- Nibble / NibbleShareのReleaseビルドと製品テスト42件が成功。失敗・skipなし。
- ビルドから作成・下書き再開・保存・検索・編集・コピー・ピン留め・削除取り消し・下書き破棄まで、標準UI driverの同一runが成功。
- 長文の下書きを含む一覧取得で、処理時間と保存層の検証プロセスの保持メモリを比較した。
- UTF-8比較は連続バッファを使う。1 MB入力の比較コストを測定し、空・NUL・結合文字・長文末尾の差をテストした。

実行コマンドは以下のとおり。`NIBBLE_SIMULATOR`に上記UDIDを指定した。

```sh
nix develop --command python3 scripts/ios.py test \
  --project-config app/project.json --configuration Release --device "$NIBBLE_SIMULATOR"
nix develop --command python3 scripts/check-mvp-ui.py --device "$NIBBLE_SIMULATOR"
nix flake check --no-update-lock-file --print-build-logs
```

UI driverは、下書き再開後・編集保存後・破棄後のコピーを、空白・改行・結合文字・絵文字を含む入力のUTF-8と照合する。削除取り消しは同じUUIDの復元、破棄は下書きの消失と保存済み本文の保持を検査する。今回のダミー項目は`74D0B4A6-9332-4600-BDC9-43743F270557`。

製品テストは実際のSQLiteとモデルAPIを使用する。古い入力順序・同じ順序で異なるUTF-8からの終了を拒否し、保存済みの新しい下書きを保持すること、消失した下書きからの別項目保存、二重保存の拒否、終了失敗後の編集継続、遅延書込による下書き再生成の防止、複数接続からの再開、ページ取得範囲を検査した。

### プロセス監視

起動時にAppleの`launchctl list`から対象bundle IDのPIDを特定し、sim-use操作の前後でホストの`ps`から同じPIDの起動時刻と実行ファイルを照合する。Simulator内のプロセス取得には数秒〜数十秒の待ち時間が生じたため、操作中の監視はホストで行う。sim-use内蔵のプロセス取得と常駐AX接続は使用しない。アプリの終了・再起動・取得失敗・複数候補は成功として扱わない。監視方式、PID、プロセス情報、実行した全コマンドはmanifestに記録する。

## 性能比較

比較対象はmainの`8dfbb18`と製品ソース`054b09d`。それぞれの保存層・モデルのソースを変更せずに取り出し、同じハーネスとApple Swiftの`-O -swift-version 6 -target arm64-apple-ios26.0-simulator`、SDK 26.5でコンパイルした。アプリの画面を起動する測定ではなく、同じiOS Simulator内の独立したプロセスで製品コードを実行した測定である。

同じSQLite fixtureのコピーを使用する。保存済み10,000件、下書き200件、各下書きの本文118,750 UTF-8 bytes。一覧は100件の表示と続きの判定に必要な取得を行う。比較対象は検索101件と下書き全文、対象実装は`library(_:)`で100件と下書き要約を取得する。

各版を3回ずつ新しいプロセスで、比較対象→対象→対象→比較対象→比較対象→対象の順に実行した。一覧は初回を除く30回、検索と入力判定は各100回。下表は3起動の中央値と、括弧内に起動ごとの値の最小–最大を示す。メモリは初回一覧を保持した時点の`task_vm_info.phys_footprint`で、アプリ全体のメモリではない。

| 指標 | 比較対象 `8dfbb18` | 対象 `054b09d` |
| --- | ---: | ---: |
| 一覧取得 / ms | 117.849（91.946–120.362） | 15.921（7.986–22.025） |
| 一覧保持時のphys_footprint / MiB | 31.583（31.568–31.599） | 9.677（9.646–9.677） |
| 1 MB入力setterと保存可否判定 / ms | 0.001（0.001–0.001） | 0.027（0.027–0.027） |
| 検索「東」/ ms | 0.183（0.155–0.201） | 0.155（0.148–0.175） |
| 不一致検索 / ms | 6.556（6.541–6.770） | 6.337（4.816–6.499） |

入力測定は1,000,000 bytesの本文の末尾1文字を交互に変更し、setterと`canSave`を呼ぶ。SwiftUIの描画・IME・自動保存は含めない。`888dec0`のUTF8View比較では同じハーネスで中央値約3.16 msを観測し、連続バッファの比較を採用した。比較対象mainは内容を照合せず入力番号を増やすため、入力setterの処理内容は同一ではない。

初期測定の不一致検索4.481→5.576 msは、1回ずつ・下書きなしの測定だった。ここに示す繰り返し測定とはデータ条件が異なる。検索SQLと検索キーは共通であり、検索の高速化や全条件の性能非劣化は主張しない。採用判断は、一覧の全文保持を削減した結果と、原文照合の契約を維持しながら入力の比較コストを抑えた結果に基づく。

ハーネス、抽出したソース、コンパイル済みバイナリ、生データ、SHA-256、集計は`artifacts/ci-performance/`に保存した。`final-summary.json`が本表の集計、`Benchmark.swift`が測定処理である。対象ソースのhashも記録した。
