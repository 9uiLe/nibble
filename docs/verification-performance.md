# 検証リードタイムの比較

[Issue #37](https://github.com/9uiLe/nibble/issues/37)で、変更の検証を開始してから自動の結果・媒体が確定するまでを比較する。アプリ自身の描画性能、人による媒体レビュー、媒体公開の時間は含めない。実行契約は[基盤設計](decisions/0001-local-ios-verification.md)、標準の入口と再現方法は[iOS手順](ios-verification.md#変更から検証を実行する)が定める。

## 環境・入力・目標

2026-09-20にApple M1 Pro / 16 GiB、macOS 26.2 (25C56)、Xcode 26.5 (17F42)、Swift 6.3.2、iOS 26.5 (23F77)の専用iPhone 17 Proで測定した。改善前は`c7d0e40`。製品ソースと依存lockを変えず、Releaseのtest→UIを直列実行した。fixtureはtest→smoke、製品は101テスト→MVP driver。テストだけtestabilityを有効にする。

改善版の`ios.py`のSHA-256は`5d276cc8c5c6a8a26d9899aa258b1b4517aa34d8b7f8799aa34c0ba0b6a74ef0`。実行時は未コミットであり、各manifestの開始・終了hashが実際の入力を示す。Nix lockは`6e96a91669e23afe13e9f8827cbcb7a0423b72b8aac15b36a673e75916a08365`、Swift Packageの共有lockは`b0bb1df2b6a012410ec0cdaa15ea64110608961fa016f9996a7dd01b24f7c381`。SDK・署名・architecture等はmanifestのenvironmentとbuild_contextに残す。

専用UDIDは`F0B5BD34-93F2-4B33-BEC7-3D5F6893440E`。各比較系列の前にこの端末のダミーNibbleアプリだけをuninstallし、同じ入力シナリオを使った。MVPは1巡ごとにダミー項目を1件残す。既存のユーザー端末は消去・削除していない。各checkoutのDerivedDataは別で、初回は新規、反復は同じcacheを再利用する。依存repositoryのグローバルcacheは保持した。依存未取得・ネットワーク速度の比較ではない。

ホストを専有しておらず、各試行のload averageも保存した。初回Simulator起動時の高負荷を通常反復へ混ぜない。製品の改善前反復は2回、改善後は3回、fixtureの反復は前後各3回。中央値・最小/最大・rangeを示し、この試行数でp95は推定しない。

基準値から、製品反復の中央値を50%以上短縮（585.620秒以下）、fixture反復の中央値を10%超悪化させない（28.656秒以下）ことを目標にした。改善後3回の連続成功と、ソース・媒体照合の成立を要求する。失敗したrunの自動再実行は行わない。UI内の既定の限定的回復はrunの再実行と区別する。

製品の連続反復は、改善前2巡を2342.410秒で完了し3.074巡/時、改善後3巡を679.924秒で完了し15.884巡/時だった。これは実際の連続測定の時間窓による値で、最速1回の逆数ではない。同じ変更なしのtest→MVP経路の比較であり、開発者の編集時間を含む生産性とは区別する。

fixtureの改善前初回testは62.519秒（起動待ち31.995秒、xcodebuild 27.808秒）。続くsmokeはAX接続で11.074秒後に失敗した。Simulatorウィンドウを表示する手作業を1回行い、新しいrunで21.231秒で復旧した。この失敗を初回成功へ書き換えていない。

製品の改善前・改善後の成功した各MVPには、標準編集メニューの既定の回復が2件ずつある。終了コード・回復理由・入力結果の照合をmanifestへ残す。これは既存driverの動作で、失敗した検証全体を再試行して成功率を上げたものではない。改善前の3回目の反復testは、中断検証のため意図的にSIGINTを送り1.805秒で失敗記録を確定した。成功速度の母集団には含めない。

## 支配的な工程と採用した変更

改善前はtestabilityの違うtest/UIを同じDerivedDataで交互に実行し、SwiftSyntax・SwiftParserを繰り返しコンパイルしていた。Releaseでは不要なx86_64も生成していた。初回testのxcresult buildは285.569秒で、SwiftSyntaxは各architectureで約139秒、SwiftParserは約66秒。並行する区間があるため単純合算しない。

改善後は実行Macのarchitectureへ限定し、testability・Debug/Release・project設定・Xcode/SDK・署名条件ごとにcacheを分けた。初回testのxcresult buildは267.380秒、SwiftSyntax127.089秒、SwiftParser64.928秒。反復testのbuildは6.500秒、続くUI buildは3.893秒となり、そのtestで新たに実行されたSwift compile sectionは0件だった。xcresultに残る過去のcached sectionは開始時刻で除外した。

| 工程 | 改善前の製品反復 | 改善後の製品反復 |
| --- | --- | --- |
| xcodebuild test全体 | 494.961 / 499.626秒 | 21.652 / 13.486 / 13.482秒 |
| UI用xcodebuild build | 449.255 / 453.551秒 | 6.153 / 3.767 / 3.781秒 |
| install・launch（MVP内5コマンド） | 再ビルドに比べ小さい | 1.486〜1.542秒 |
| sim-use（MVP内192コマンド） | 前後のプロセス確認を実行 | 171.482〜172.814秒、確認を維持 |
| PID確認（MVP内384コマンド） | 各確認を個別表示 | 2.557〜2.775秒。内部表示だけをUI工程へ集約 |
| manifest書込 | 個別記録を維持 | 1243回、1.732〜1.863秒 |
| 最終ソース・媒体hash等の確定 | 検証を維持 | 0.123〜0.145秒 |

工程には入れ子の時間があるため、表の値を総時間として合算しない。全体の開始から終了まではbenchmark結果、内訳はmanifestのcommandsとtimingを参照する。同一run内の重複bootstatusを省いたが、runの開始時には端末の準備を確認する。

revisionのファイルごとにGitを起動していた証跡照合は2.793〜4.580秒だった。128 blobずつのbatch読取へ変更し、196ファイルで0.083 / 0.052 / 0.053秒となった。binary、空ファイル、改行・日本語を含むパス、同一blob、不完全な応答を回帰検査する。

Xcodeによる毎回の増分検査、実行前のbundle/executable検査、同一UDIDの排他、操作前後のPID照合、fresh AX接続、通知期限とRive周期の観測待ちは維持した。インストール済みアプリだけを根拠にビルドを省かない。cache分離には初回準備と保存容量が必要である。

## 候補・変更・失敗の比較

同じwarm test cacheで通常の`test`と`build-for-testing`→`test-without-building`を交互に各3回比較した。全実行で101テストが成功した。通常方式は20.386 / 14.923 / 15.087秒（中央値15.087秒）、分割方式は17.398 / 17.313 / 17.531秒（中央値17.398秒）。この条件では分割方式の利点がなく、別の成果物照合契約も必要になるため採用しない。実験wrapperとそのhashを保存し、この候補のrunを最終の証跡として使わない。

同じnative architectureでもcacheを共用してtestabilityを切り替えると、warm test 15.025秒の後のUI用buildが234.650秒へ増えた。architecture限定だけでは再ビルドを解消できないため、構成ごとのcache分離を採用する。

静的検査との重なり、代表変更、失敗と復旧の測定は継続中。最終評価時に結果・採否・未達条件を記録する。この節が未確定の間はIssue全体の受け入れ完了を意味しない。

## 再現と証跡の範囲

`artifacts/issue37/native-*/results.json`に全試行、argv、工程時間、source hash、ホスト負荷、runの対応を保存した。改善前は基準checkoutの`artifacts/issue37/baseline.json`。`artifacts/ios/<run>/`がxcresult、詳細ログ、画像・録画、開始/終了の入力と媒体hashを所有する。生成物はGit管理対象外で、文書だけから媒体の観測済み状態を推定しない。

再現には[iOS手順の比較コマンド](ios-verification.md#検証時間を比較する)でtest→MVPまたはtest→smokeのargv列を指定する。初回は新しい専用DerivedData、反復はそのまま同じUDIDとcacheを使う。異なるcheckout・SDK・構成・データ量・ホスト負荷の値を同条件として混ぜない。通常の開発では`verify.py plan/run`を使い、測定のための反復実行を毎回要求しない。

媒体はローカルの画像と録画抽出フレームで確認し、review.jsonに観測した時刻・内容を記録する。全編連続再生・媒体公開・ブラウザー閲覧は未実施。これらは自動処理の成功やローカルの抽出確認で代替しない。
