# エージェント指示の設計

## 目的と適用範囲

nibbleのエージェント指示は、作業に必要な製品知識・実装契約・実行手順を参照できる構成とする。エージェントは依頼された成果物と変更の影響から手順を選び、許可された範囲の編集・検証を完了まで進める。参照資料の量や工程数を固定せず、品質条件と権限境界によって作業範囲を定める。

本書は指示を設計・保守する参加者向けに、文書の構成、責務、参照方法、検証の基準を定義する。日常の開発は[AGENTS.md](../AGENTS.md)を入口とする。リポジトリ内の指示と`.agents/skills/nibble-verification/`は、エージェントの製品やモデルによらず共有する。ホームディレクトリのSkill、プラグインのキャッシュ、グローバル設定はリポジトリの管理対象外とする。

## 文書の構成と責務

正本は、規約や手順の詳細を定義する文書を指す。入口となる文書には判断に必要な要点と参照条件を置き、正本へ案内する。

| 文書 | 責務 | 参照する作業 |
| --- | --- | --- |
| [AGENTS.md](../AGENTS.md) | 製品の判断基準、実装の主要契約、実行コマンド、権限境界、完了条件 | リポジトリ内の作業全般 |
| [CONTRIBUTING.md](../CONTRIBUTING.md) | 開発環境・実装・検証・公開の詳細規約 | 作業内容に対応する節 |
| [nibble-verification/SKILL.md](../.agents/skills/nibble-verification/SKILL.md) | iOS実行・証跡照合・媒体レビュー・PRの工程選択と入出力 | 検証の実行、runの確認、証跡の整理、PR作成・更新 |
| [local-ios.md](../.agents/skills/nibble-verification/references/local-ios.md) | 検証対象の選択、Simulator操作、失敗の切り分け | iOSを実行する検証 |
| [証跡とPRの検査](review-evidence.md) | ソース照合、媒体形式、レビュー記録、添付と閲覧、PR本文の検査 | runの利用、媒体共有、PRの準備と公開後の確認 |
| [Rive用AGENTS.md](../app/Animations/about/AGENTS.md) | `about/`の制作に用いるCLIと確認方法 | RML・Rive設定・説明イラストの変更 |

[about/CLAUDE.md](../app/Animations/about/CLAUDE.md)は`@AGENTS.md`で同じディレクトリの制作規約を参照する。Riveのソース、生成済み`.riv`、manifest、iOSへの接続は[アセット手順](../app/Animations/README.md)が定義する。

## 参照とSkillの選択

Skillの`description`は、提供する作業と発動条件を示す。nibble-verificationの対象はiOS検証の実行、runと証跡の照合、PR作成・更新である。静的検査だけで完結する作業は、AGENTS.mdから検査コマンドへ進む。

Skill本文は、各工程の入力・成果物と共通の注意点を持つ。Simulator操作の詳細はiOS実行時に、媒体の添付手順は公開時に参照する。ローカル検証、媒体公開、PR作成はそれぞれ独立した作業範囲として選択できる。

開発ガイドと参照資料は該当する節を読む。確認済みで内容が変わっていない資料は再利用できる。参照リンクには用途を添え、ファイルを移動する場合は参照元も更新する。

## 検証工程の入出力

runは、1回のiOS検証で得られる対象ソース・端末・コマンド・成否・媒体の記録である。`manifest.json`は実行条件とファイルの照合情報、`review.json`は確認者の観測と閲覧条件、`REVIEW.md`はそれらを共有するための文書を持つ。

| 工程 | 入力 | 成果物と成立条件 |
| --- | --- | --- |
| ローカルiOS実行 | 対象project、期待結果、iOS 26.5の専用UDID | 対象destinationでビルドして実行したrun。画面確認では画像・録画も保存し、対象ソースと実行結果を対応付ける |
| runの照合・再利用 | runと照合先のGit revision | `check_evidence.py --integrity-only`によるソース・成否・媒体の一致。文書だけの変更でも、runを再利用する際には照合が必要 |
| 媒体レビュー | 照合済みrunと確認範囲 | 実際に開いた画像、再生・抽出した動画の観測を記入した`review.json`。確認時刻・方法・未実施条件を明示 |
| 媒体公開 | 公開する媒体と保存先 | ダミーデータの原本、安定したURL、ブラウザーでの読込結果。証跡検査後の`REVIEW.md`で共有 |
| PR作成・更新 | base/head、全コミット、検証結果、必要な媒体 | 本文と全コミットの一致、最終headのCI成功、閲覧可能な証跡。UI対象外の場合も証跡欄に理由を記載 |

ビルド用cacheやコミット名だけではrunの再利用を判定しない。実行中の入力変更を失敗とし、失敗runも保存する。自動実行、動画デコード、抽出フレーム確認、全編再生、アップロード、ブラウザー閲覧は別々の確認として記録する。公開を伴わないローカル検証では、公開・閲覧を未実施として報告する。

## 品質条件と権限境界

実装は[ライブラリ規約](library-policy.md)に従う。操作APIの完了、タスク所有、Viewの比較、アニメーションの適用範囲をそれぞれの契約で検証する。比較ゲート単体は環境更新を遮断しないこと、製品の入口は[固定表示方針](design/decisions/0002-fixed-interface.md)を適用することを確認する。[UI設計](design/README.md)は採用仕様・判断理由・設計IDを持ち、監査は不足と改善候補、検証記録は対象ソースに対する観測を持つ。

依頼の範囲内の調査、編集、ローカル検査、変更に起因する失敗の修正と再検査は、工程ごとの承認を求めず進める。承認は対象操作と範囲に対して扱い、承認済みの同じ範囲について重ねて確認しない。

PR作成の依頼はマージやリポジトリ権限変更を含まない。依頼に含まれない公開・マージ・権限変更、および手順で承認が要求される操作は、承認を得てから行う。承認待ちの間も独立して実行できる編集・検証は進め、確認時には対象操作と根拠を示す。

Simulatorの既存端末は消去・削除しない。Xcodeマクロは[セットアップ手順](../README.md#3-xcodeとswift-packageを準備する)に従って固定revisionを照合し、対象パッケージを個別に承認する。[配布手順](testflight.md)と[配布設計](decisions/0003-testflight-distribution.md)は、秘密情報を利用できる経路と担当者の責務を定義する。エージェントは秘密情報を直接参照せず、レビューした配布スクリプトによる署名・アップロードと公開manifestの確認を担当する。

## 検証と完了の基準

[検証基盤の設計](decisions/0001-local-ios-verification.md)に従い、静的検査、iOS実行、証跡照合、レビューを別の保証として扱う。文書だけの作業は、差分・適用条件・正本との整合と共通検査で確認する。Swiftや実行環境の変更では対象targetのビルドと影響する契約のテストを行い、UI/UX・操作・性能への影響に応じて画像・録画・同条件の測定を加える。

依頼された成果物と必要な検証をそろえ、実施結果と未実施・未解決の条件を報告する。マージには[証跡とPRの検査](review-evidence.md#githubの必須チェック)が定義する証跡・本文・CI・base追従の条件を満たす必要がある。必要な検証が残る場合は、その条件を明記し、検証済み・マージ可能とは報告しない。

指示の保守では、次の観点で確認する。

- `scripts/check_docs.py`で相対リンク・見出し・Skillメタデータ・設計文書の整合を確認する。
- Skillの発動条件が、実行する作業と一致するかをレビューする。文書修正、ローカル検証、媒体共有、PR、配布をそれぞれ独立して選べることを確認する。
- 実行スクリプトや機械判定する規約を変更した場合は、影響する動作と不変条件を回帰テストで検証する。
- 指示の文面と機械検査だけでは、実際の選択精度や作業時間は判定しない。利用時に問題を観測した場合は、対象の依頼・適用した指示・結果を記録して評価する。

## 設計の根拠

[Rethinking skills and prompts for GPT-6 Astra — OpenAI Developers](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)（Eric Provencher、2026-09-11）は、Skillの明確な発動条件、作業に応じた資料の参照、完了条件の定義を示している。

“progressive disclosure”は、Skill本文を工程選択の入口とし、詳細を必要時に参照する構成の根拠とする。“define completion before starting”は、各工程の成果物と成立条件を定義する根拠とする。指示は複数モデルで共有するため、特定モデルの能力を承認・品質条件の前提にしない。
