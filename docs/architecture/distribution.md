# TestFlight内部配布の設計

TestFlightは、署名済みnibbleを配布担当者本人の端末へ届ける経路である。開発と同じmacOSユーザーでローカルarchiveと送信を行い、App Store Connectの内部グループ「本人用」へ自動配信する。外部テスト・App Store公開はこの配布範囲に含めない。

## 構成と責務

| 担当 | 責務 |
| --- | --- |
| 製品config | 本体/共有/Keyboardの識別子、同じApp Group、version、暗号申告を定義 |
| 配布スクリプト | 設定検査、共通検査、固定依存解決、Release archive、完成物検査、署名・送信、公開manifestを生成 |
| エージェント | レビュー済みスクリプトを実行し、署名・送信の成否と公開メタデータを確認 |
| 配布担当者 | Apple登録・認証設定・署名資産、Apple側処理/配信、実機の確認 |

本体と各拡張は別profileで署名し、同じTeam/App Groupとversion/buildを持たせる。詳細な識別子・設定書式・実行方法は[TestFlight手順](../testflight.md)へ集約する。

## 秘密情報と実行の境界

認証設定・API秘密鍵・生ログはリポジトリ外の~/.appstoreconnect、署名秘密鍵は担当者のKeychainへ置く。エージェントは直接読まず、別コマンドやコード変更で迂回しない。会話への貼付けも求めない。使用できる経路はレビュー済み配布スクリプトの設定確認・archive・署名・アップロードである。

同一ユーザー内の行動規約であり、OSの読取権限を分離するものではない。deny設定は補助に限る。スクリプトは設定をshellとして実行せず、所有者・権限・link・識別子・鍵パスを検査する。秘密鍵本文はPythonへ読み込まず、Xcodeへパスを渡す。

表示に渡すのは工程名・成否・公開メタデータだけとする。生ログと実際の認証値・例外詳細を表示しない。設定の登録変更とエラー調査は担当者が行い、秘密を除いた原因だけを共有する。

## ビルドと送信の契約

コミット済みのクリーンなソースから、lockを更新せずにビルドする。完成archiveの識別子、拡張、version、権限、暗号申告を検査してからexport/uploadする。検査が製品を推測して書き換えることはない。

Swift Packageの解決前に、[RiveRuntimeのローカルビルド](presentation.md#描画先の取得)を完了する。この工程は認証・署名を使わず、固定ソースとpatchから生成したXCFrameworkを検証する。準備に失敗した場合はarchive・送信へ進まない。

実行記録はbuild番号ごとに分離し、上書きと同じcheckoutの並行配布を防ぐ。送信中断で受理状況が不明なら自動再試行しない。担当者がApple側を確認し、必要な場合だけ新番号で実行する。表示の失敗と送信の失敗を混同しない。

## 輸出コンプライアンスの申告

製品はAppleのData Protectionを使い、独自暗号実装を持たない構成としてInfo.plistに免除対象外の暗号化なしを申告する。この申告は実際の機能/依存に基づく製品設定であり、配布時に自動推測しない。依存や暗号機能の変更時は担当者が適合性を再評価する。

## 配信と完了条件

エージェントの完了は署名・upload成功と公開manifestの確認。Apple側の処理・本人用への反映・インストール/実機の成否は担当者が別に確認する。通常の配布でエージェントのブラウザーサインインや配信状態確認は不要とする。

配布先人数、外部公開、認証主体、署名管理、データ利用が変わる場合は信頼境界と手順を再設計する。
