# 検証とレビュー基盤の設計

検証基盤は、変更に必要な検査を実行し、ソース・操作結果・画面の観測をレビュー対象へ対応付ける。対象に応じた実行計画と構成別のビルドキャッシュで待ち時間を抑え、保存済みの観測から必要な情報を取り出してAIの入力を抑える。実行の記録、閲覧用のデータ、確認者の判断をそれぞれ管理し、確認できた範囲を明示する。

この文書は構成・責務・実行契約を定義する。変更種別ごとの受け入れ条件は[開発ガイド](../../CONTRIBUTING.md#実行と検査)、コマンドは[iOS手順](../ios-verification.md)、媒体とPRの確認は[証跡手順](../review-evidence.md)を参照する。

## 検証の単位と構成

**検証計画**は、変更ファイルから選んだ検査、選択・除外理由、事前条件、手動確認事項をまとめたもの。**検証実行**は、その計画に従う一連の工程であり、一つの`result.json`に結果を保存する。**run**は、個別のiOSコマンドが生成するソース・端末・成否・媒体の記録である。一つの検証実行には複数のrunが含まれる。

| 構成 | 責務 |
| --- | --- |
| `verify.py` | 差分からの計画、工程の順序と中断、工程結果とrunの対応、証跡の整合性確認、保存済み状態の要約 |
| 対象config・`ios_project.py` | Xcode project、scheme、bundle ID、署名方式、検証入力の選択 |
| `runtime/rive/`・`rive_runtime.py` | ネイティブ描画基盤の固定入力・unsigned生成・キャッシュと完成物照合 |
| `verification_catalog.py` | 工程ID・コマンド・対象configの参照。scheme等をconfigから独立に定義しない |
| `ios.py` | `simulator_lock`による端末の排他、環境確認、ビルド・テスト・インストール・起動・撮影、runの確定 |
| `product_ui.py` | 作業画面への復帰、本体・共有エディターの入力位置と表示切替の識別 |
| 対象別UI driver | 利用者の操作と対象機能の期待結果。画面遷移は`Run.wait_ui`へ到達条件を渡す |
| `manifest.json` | runの開始・終了ソース、端末、コマンド、成否、媒体hash、所要時間 |
| `inspect_ui.py` | 保存済みの画面要素の要約・差分と、PNGの閲覧用画像の作成 |
| `review.json` | 確認者が実際に観測した内容、対象媒体、確認方法、未確認条件 |
| `check_evidence.py` | runと指定revision、媒体、レビュー申告の照合 |
| `benchmark_verification.py` | 明示したコマンド列の反復測定、工程時間・ばらつき・完了数の集計 |
| `check_pr.py`・Ubuntu CI | PR本文と全コミット、変更範囲、最終headのCI、共通静的検査 |

各工程のstdoutは`<工程>.log`、stderrは`<工程>.stderr.log`へ分けて保存し、resultの`log`と`stderr`で参照する。CLIが入力・結果データ・終了コードを管理し、工程や成否の表示は`script_ui`の表示Adapterを通してhamioへ渡す。入出力と表示障害の扱いは[スクリプト設計](../script-tooling.md)に定義する。

## 検証範囲と工程の順序

自動計画は、比較元のコミットと作業ツリーの差分を使う。コミット済み・ステージ済み・未ステージの変更に加え、未追跡ファイルと削除も対象にする。計画中・工程間・終了時にソースを照合し、入力が変わった検証実行は失敗にする。

すべての計画に共通静的検査を含める。画面要素の解析は共通回帰で検査し、画像加工とそのCLIにはローカルMacの`preview-native`を選ぶ。文書や静的検査だけの変更ではiOSを選ばず、製品・fixtureの専用テストの変更では対象targetの全テストを選ぶ。製品実装には製品テストとUI導線、個別UI driverにはその導線を対応付ける。実行基盤のfixture変更にはfixtureを、共通基盤・設定・分類できない変更には通常回帰全体を選ぶ。性能targetは目的・条件を決めて明示的に選択する。通常回帰の対象と削除・統合基準は[テスト設計](../testing.md)に従う。具体的なファイル区分は`verify.py`とその回帰テストが定義する。

対象targetのテストは全件実行する。ファイル名から個別テスト名を推定して絞る方式は、間接的に影響する契約を取りこぼすため使用しない。OS連携の手動操作、性能測定、媒体の目視は自動工程と別の確認事項として計画に残す。明示的なscope指定は実行範囲の指定であり、その範囲だけの成功を全対象の合格として扱わない。

共通静的検査、選択されたmacOSの画像試験、対象targetのテスト、UI操作の順に実行する。静的検査で分かる失敗をiOS起動前に返し、テストで契約を確認してから画面操作へ進む。`preview-native`はSimulatorを操作せず、iOSのrunを生成しない。選んだ工程の失敗で後続を停止し、未開始工程を結果に残す。工程単位の自動再試行は行わない。

成功後の再計画には`--since`で指定した結果のソースsnapshotを使う。全工程が成功し、開始・終了ソースが一致する結果だけを受理する。再計画の結果は追加差分の検証範囲を示し、参照元の結果や媒体レビューを置き換えない。未解決事項が残る導線は、その条件を解決する検査として明示する。

計画は選択・除外理由とソースsnapshotを`plan.json`へ保存する。stdoutには工程・準備事項・手動確認・詳細への参照を返す。内容の多いソース情報を必要なときだけ読める一方、判断の根拠はファイルに残る。計画時点のソースが実行時点と同じとは限らないため、`run`は実行時に計画を作る。

状態の要約は記録済みの成否を保持し、現在のソースとの差分を表示する読み取り操作である。自動再開や成功工程の再利用判定は行わない。実行の寿命は起動元のプロセスが管理し、保存された`running`を生存確認に使わない。結果ファイルは同じディレクトリ内の一時ファイルから置換し、実行中の読取へ部分的なJSONを渡さない。

## 端末と実行環境

補助ツールはflakeとlock、製品依存は共有`Package.resolved`で固定する。Xcode・SDK・SimulatorはローカルMacのApple配布物を使い、NixのC toolchainでApple compilerを置き換えない。ツール、OS、runtimeのbuildをmanifestへ記録する。

iOS実行は明示したiOS 26.5の専用UDIDとダミーデータを使う。UDIDは同名の端末を区別する識別子である。共通driverと保存層の測定は同じ`simulator_lock`で同一UDIDへの同時実行を拒否する。直接のsim-useやXcode操作はこのロックに参加しないため、利用者が同じ端末への操作を直列化する。既存端末の消去・削除は行わない。

ビルド・実行管理・撮影はApple CLI、画面の読取・入力はNixのsim-useが担う。閲覧用画像の加工にはmacOS付属の`sips`を使う。一つのrun内では完了した端末起動確認を共有し、各runの開始時には端末の準備を確認する。

## ビルドキャッシュと成果物

DerivedDataはXcodeの中間生成物と増分ビルド情報を保存するキャッシュである。保存先をUDIDとビルド条件のhashで分け、異なる端末や構成が同じ中間生成物を更新しないようにする。

| ビルド条件 | 分離する理由 |
| --- | --- |
| 対象config・`ios_project.py` | project・scheme・bundle・署名の異なる対象を区別する |
| Debug / Release | 最適化条件を区別する |
| testabilityの追加有無 | 内部APIを検査するテストと、通常のUI実行のコンパイル条件を区別する |
| 実行Macのarchitecture | Simulatorを実行するCPU向けの成果物を生成する |
| Xcode・Swift・SDK・Developer Directory | compilerとSDKの組み合わせを区別する |
| Simulator署名引数 | 署名とentitlementの条件を区別する |

標準の検証計画はReleaseを使う。テスト時だけ`ENABLE_TESTABILITY=YES`を追加し、UI実行の最適化は対象projectのRelease設定に従う。architectureは実行Macに限定する。テストとUIで中間生成物を分離すると、構成を交互に使う際の依存再コンパイルを避けられる一方、構成ごとの初回ビルドと保存容量が必要になる。

すべてのbuild・test・launchで`xcodebuild`を実行する。ソース、Xcode project、依存lockの変更はXcodeが増分検査し、必要な再ビルドまたは失敗を返す。lockにない依存版の自動解決は許可しない。ビルド成功後にbundle IDとapp内の実行ファイルを確認してからインストールする。

Rive描画基盤は各ビルド前に同じ`prepare`で照合する。証跡の入力には対象target・scripts・runtime・flake/lockを含め、基盤定義の変更もiOS検証の結果を無効にする。

キャッシュの存在、インストール済みアプリ、別runの成功は実行ソースの証明には使わない。証跡の根拠は同じrun内の対象scheme・UDIDへの成功したbuildまたはtestと、そのrunのソース照合である。

## 操作・失敗・中断の判定

テストは`xcodebuild`の終了コードとxcresult summaryで判定し、成功1件以上・失敗なしを要求する。0件・全skip・timeoutは失敗となる。既知の終了コード1をdriverが処理する場合だけ、理由と対応するassertionの成立を記録する。

画面取得と入力の前後で、起動したアプリのPIDとprocess情報を照合する。sim-useは操作ごとに新しいアクセシビリティ接続を使う。内部のPID照合はログと成否を保存し、進捗表示は対応するUI工程へまとめる。

遷移中の空の画面情報は、有限回の待機と最終状態の判定を持つdriver内でのみ許す。ツールの失敗、対象processの終了、任意の操作失敗を正常化しない。状態への到達を待つ処理と、通知期限・演出周期を観測する時間を区別する。文字列はOSの入力・コピー経路を通して原文を比較し、テスト用DBやclipboardの直接書換えで結果を作らない。

検証実行のtimeout・中断では、実行中の工程のprocess groupへ停止を通知し、後処理を待つ。期限内に終了しない場合は強制停止して回収する。中断を処理できたdriverはrunを失敗として確定し、取得できたログ・媒体を保存する。強制停止などで未確定のrunは成功の根拠にしない。失敗した実行は上書きせず、再実行には別の結果ディレクトリを使う。同じrunで同名のコマンド・画面観測・撮影を繰り返した場合も、連番のファイルに保存する。manifestの各コマンドから、その実行時のstdoutとstderrを参照できる。

## 画面の観測と閲覧用データ

Simulatorの画面確認には、操作の状態、外観、時間変化に対応する観測を使う。accessibility情報は、画面上の要素の役割・識別子・文言・値・状態・座標を表すデータである。表示の細部は画像で、動きは録画で確認する。

| 確認対象 | 読み取る情報 | 判断の限界 |
| --- | --- | --- |
| 操作先、入力値、選択、要素の出現・消失 | sim-useのaccessibility情報とその差分 | 色、重なり、描画だけの要素は判断できない |
| 配置、表示の欠落、文字切れ、装飾 | 全体の閲覧用画像と必要な領域の原寸画像 | 縮小や切出しで見えない細部・領域は未確認になる |
| 操作中の遷移、一時的な表示、演出 | 原本の時刻に対応する録画・抽出フレーム | 抽出時刻の間の挙動は連続再生で確認する |
| 応答や描画の性能 | 条件をそろえた測定 | 画像や録画の印象だけでは性能を判定できない |

実行時のJSON・画像・録画を原本として保存し、AIには確認項目に必要な情報を渡す。`inspect_ui.py`は保存済みファイルを入力にする。Simulatorへの操作、合否判定、レビュー記録の更新は、それぞれ実行driverと確認者が担当する。

`tree`は要素の項目と表示件数を絞り、省略した件数・文字列長を出力する。差分は抽出した項目の完全な値と出現個数で計算し、表示時に文字数を制限する。要素の順序は比較せず、座標の比較は明示的に選ぶ。入力ファイルとhashを出力に含め、必要な原文を再読できるようにする。

`image`はPNGをデコードし、縮小・切出しした閲覧用画像（preview）を生成する。原本の複製を変換し、処理終了時に原本の一致を確認する。派生画像はどのrunにも属さない新しいディレクトリへ保存する。`preview.json`には原本と派生画像のhash・寸法・切出し範囲・倍率・変換コマンドを記録する。run内への出力、既存出力先、原本を越える切出し範囲を拒否する。出力先を作成した後の失敗は`failure.json`へ残す。

この構成では、操作の確認ごとに画像全体を入力する必要がなく、外観の確認に必要な解像度は対象領域ごとに選べる。閲覧用データの生成成功が保証するのは処理の成立であり、画面の正しさは確認者が判断する。公開インターフェースと開発方法は[観測データの確認](../simulator-inspection.md)、目視の手順は[画像の全体と細部の確認](../review-evidence.md#画像の全体と細部の確認)を参照する。

## 証跡とレビューの境界

runは開始・終了の検証入力と、確定した媒体のhashを持つ。入力が実行中に変わった場合は失敗とする。検証実行は自身が開始したrunだけを集め、ソース・媒体に加えてUDID・Release構成・対象configの全フィールド・コマンドが計画と一致することを照合する。

製品UIの共通入力は`verification_catalog.PRODUCT_UI_INPUTS`に列挙する。計画は編集工程と共有の手動確認へ対応付け、証跡の入力hashにも同じファイル集合を含める。入力例だけを変えた結果を、異なる例の成功runで認定しない。

指定revisionとの照合はコミット名ではなくファイル内容を使う。Gitのblobをまとめて読み出し、binaryと改行を保ってファイルごとのhashを比較する。これによりファイルごとのGit起動を避けながら、追加・削除を含む入力の一致を確認できる。照合対象と媒体の要件は[証跡手順](../review-evidence.md#runのソースと結果)に定義する。

入力が一致するrunは別revisionでも再利用できる。記録のないhashを事後推定して加えない。単独の撮影は、インストール済みアプリのソースを保証しない補助資料である。画像の目視、動画の抽出確認、全編再生、公開先の閲覧は別々に記録し、自動の整合性検査で代替しない。

レビュー記録は原本の媒体名とhashを対象にし、閲覧用画像を使った場合は確認範囲と変換条件も記載する。同じ原本・範囲・確認項目の観測は再利用できる。別の状態や確認項目、見落としの懸念がある場合は該当箇所を確認する。画像の添付、媒体hashの照合、観測内容の判断はそれぞれ独立した工程である。

## 実行方式の選択と評価

| 採用方式 | 判断理由と適用条件 |
| --- | --- |
| 対象別の全テストとUI導線 | 変更の範囲を絞りつつ、target内の契約の選択漏れを避ける |
| `xcodebuild test`と構成別キャッシュ | 同runにビルド成功・ソース・実行結果を記録し、増分ビルドで必要なコンパイルを実行する |
| 静的検査を先に行う直列工程 | 静的な失敗でiOSを開始しない。工程の重なりによる短縮量に対し、中断と証跡管理の負担を抑えられる |
| 一つの専用Simulator | 画面・クリップボード等の共有状態を直列に扱う。Swift Testing内の独立テストの並行性と、別Simulatorを使うXcodeの並列実行は区別する |

方式の評価には、自動処理開始から必要な結果と媒体の確定までを測る。明示したコマンド列の一巡を検証サイクルとし、工程時間、中央値、ばらつき、測定時間窓内の完了数を記録する。初回・反復・代表編集・失敗と復旧を別条件にし、人による修正・媒体レビュー・公開は自動処理時間へ含めない。条件と観測値は対象ソース付きの`artifacts/`へ記録する。コマンドは[検証時間の測定](../ios-verification.md#検証時間を比較する)に定める。

AIの入力効率は、同じ確認項目に対する判断の成立と、入力した画像数・寸法・テキスト量で評価する。token数や料金は、使用モデルと実行環境の使用量を取得できた場合に記録する。ファイル容量・画素数・文字数の減少率をtoken削減率へ読み替えない。

## CI・マージ条件・保証範囲

共通検査はApple SDK・Simulator・GitHub認証を必要としない。全CI jobは`ubuntu-24.04`を直接指定し、macOS runnerの間接起動も許可しない。iOS実行・性能・媒体の内容はローカルMacの責務である。

PRのマージには必要な検証、本文と全コミット、閲覧できる媒体、最終headのCI、baseへの追従を要求する。ruleset宣言と実効GitHub設定は[証跡手順](../review-evidence.md#githubの必須チェック)で照合する。

構文検査は型と実行を、hash照合は観測の真実性を、Simulatorは実機条件を証明しない。判定可能な不変条件は違反例を含む回帰テストで検査し、画面・性能・人の判断に属する条件は対象と方法を明示して確認する。
