# テストの設計と選択

テストは、利用者の入力や保存済みデータを失う、違う対象へ作用する、失敗を成功として扱う、といった現実的な不具合を検出するために置く。件数とカバレッジ率は維持目標にしない。製品の期待動作は[製品仕様・要件](product-specification.md)、検証の実行契約は[検証基盤](architecture/verification.md)が定義する。

## 保証の置き場所

| 種別と配置 | 防ぐ不具合・評価する条件 | 実行 |
| --- | --- | --- |
| `app/NibbleTests/` | 原文破損、競合更新、下書きの復活、古い非同期結果の反映、誤った入力先への作用、画面の寿命・描画入力の欠落 | `product-test`。選んだtarget全体を実行 |
| `app/TestSupport/` | 実画面をホストするwindowとruntime観測。回帰と測定で使う補助コード | 各test targetから利用 |
| `scripts/tests/` | 誤った成否、証跡の取り違え、入力拒否の欠落、CLIの出力混入、静的規約違反 | Nix共通検査 |
| `tools/ui-design/tests/` | 設計入力の変更見逃し、壊れた台帳の受理、製品間の状態混入 | Nix共通検査 |
| `scripts/tests/macos/` | 実デコーダーの失敗、縮小・切出し位置の誤り、原本・runの破壊 | `preview-native`。ローカルMacのsipsを使用 |
| `validation/VerificationApp*` | 共通コマンドでのビルド・テスト・入力・コピー・撮影の不成立 | `fixture-test` / `fixture-smoke` |
| `scripts/check_*_ui.py` | 製品の実操作、ナビゲーション、フォーカス、表示設定との接続不良 | 対象のUI工程 |
| `app/NibblePerformanceTests/`、benchmarkスクリプト | 時間・メモリ・反復時の保持量。条件と予算をそろえて評価 | 明示的な性能測定 |

通常回帰は製品・実行基盤・開発ツールを対象にする。`verify.py`の`auto`は差分から選び、`regression`は通常回帰全体を選ぶ。性能は`performance`を明示する。共通設定の変更でも測定を自動で追加しない。測定のソース変更は計画の`manual_review`に実行先を示す。コマンドと事前条件は[実行手順](ios-verification.md#変更から検証を実行する)を参照する。

## 残す・統合する・削除する基準

各テストについて「削除すると見逃す現実的な不具合」を説明する。同じ操作・境界・結果を別のテストが確認していれば、固有のassertionをそこへ移して統合する。fixtureを変えても通る処理が同じなら、ケース追加の理由にならない。DB読取とモデルの結果反映、キャンセル要求と結果反映の資格、入力先変更と権限変更など、独立した境界は別のケースとして残す。

実装を写した期待値の計算、モックへ設定した値の読み戻し、型システムや外部ライブラリだけの保証、私有フィールドの反射、内部の呼出し回数は製品の回帰条件にしない。外部APIには実際のアセット・一時DB・デコーダーを接続し、自分たちが所有する契約を確認する。モックや継続のゲートは、実モデルへ失敗を返す、処理順序を逆転させるなどの入力制御に使う。

非同期の順序は開始・完了ゲートで固定する。通常回帰に時間の上限を性能予算として混ぜない。描画の停止や通知期限そのものを観測する場合は、必要な待機区間とその根拠を明示する。同じ状態への反復は、累積保持や負荷が目的の測定へ置く。

削除の前には、固有の失敗条件を統合先で再現できることを確認する。実行時間だけでなく、不安定さ、依存更新やリファクタリング時の修正負担も保証の価値と比較する。「念のため」だけでは残さない。

## 入力・一覧・描画基盤の回帰

一覧モデルは実DBと完了ゲートを使い、3集合の一括取得、切替時の読込要求なし、集合ごとのページ上限、外部更新の明示取込、遅延・取消・不完全な結果の拒否を検査する。検索・削除一覧の要求と通知元は画面種別で固定する。

Markdown編集は原文のUTF-8、装飾範囲、選択、IMEの未確定文字、マウント時のフォーカス、プレビュー往復での入力View・選択・Undoの保持をhostedテストで確認する。プレビューの記号除去・見出しと強調の書式・段落とリストの区分を解析結果で確認し、保存後は原文のUTF-8を照合する。LF・CR・CRLFとその混在、NUL、結合文字・絵文字を含む原文でも、装飾が意図した文字へ適用されることを検査する。本文の解析番号と下書きの保存番号は別に検査し、タイトルの変更や完了後の入力で不要な解析を始めないことを保証する。ソフトウェアキーボードとの実際の重なりはOS導線で確認する。

変数の印は、本文のUTF-16選択範囲を置換する場合、位置がないため末尾に追加する場合、無効な位置で原文を保持する場合を製品テストで分けて確認する。名前ごとの入力欄、原文から完成文への切替、確定前の取消、コピー・Keyboard入力の作用は[変数の操作手順](ios-verification.md#変数の編集と利用を確認する)で表示とOS作用を照合する。

Rive描画基盤はキャッシュの入力・生成物の照合をPython、フレーム進行と終了後の再開防止を製品の実runtimeテストで検証する。画面側の停止・再開と基盤の取得待ちは別の契約である。

## 製品UI工程の責務

| 工程 | 主な確認 |
| --- | --- |
| `library-ui` | 入力、下書き再開、検索、編集、原文コピー、ピン、破棄、削除一覧からの復元、再起動後の右側操作 |
| `notice-ui` | 起動直後のコピー通知、コピーから削除への通知置換、同じ項目の取り消し、検索入力・フォーカスの維持、期限、スクロール、離脱時の消去 |
| `controls-ui` | 作業画面の検索欄が初期状態で非フォーカスであること、設定のバージョン・削除一覧、編集の操作領域と排他、タイトルから本文への入力、Markdownプレビュー往復、タイトル・本文を保持した補足往復とフォーカス復帰、呼出元と一覧フィルターの保持 |
| `interface-ui` | 一覧・編集・設定・両説明画面の標準／最大文字サイズ・コントラストに対する表示固定 |
| `about-ui` / `keyboard-guide-ui` | 実アセットの再生、ライト／ダーク、背景復帰、Reduce Motion切替、本文末尾への到達。Keyboardは`--story keyboard`で選ぶ |

Riveの通常回帰は、可視境界の両側、停止理由の合成、停止中の配色・寸法変更、Sessionの独立性と所有資源の解放を確認する。各アセットの同じ境界を反復するだけのケースは増やさない。時間・メモリの予算は[性能手順](performance-verification.md#riveの補助指標)に置く。

通知の通常回帰は冷起動1回で対象の境界を検査する。反復起動の負荷を調べる場合は`check_notice_ui.py --cold-launches`へ2〜20回を明示する。Markdownの改行・NUL・装飾は座標変換の異なる境界、静的検査は異なる構文経路ごとに代表ケースを置き、等価な入力の直積を作らない。

Markdownの通常入力例は[EditorMarkdown.txt](../validation/EditorMarkdown.txt)を使う。`controls-ui`を標準幅・狭幅の専用端末で実行し、同じ入力操作・表示切替を検査する。共有拡張は[ShareHost](../validation/ShareHost.html)で同じ例を読み込み、保存後のコピーまで原文を照合する。

画像・録画の取得成功と、内容の観測、性能の合否は別々に記録する。連続した演出は録画を原本にし、確認用の静止画を時刻付きで抽出する。抽出フレームだけで全時間区間を確認済みにはしない。

## 検証範囲と制約

検査の存在は対象ビルドでの合格を意味しない。現在のcheckoutへ適用できる結果は、[証跡手順](review-evidence.md)で対象ソースとrunを照合する。保存層・モデルのテストは永続化、競合、await直後の結果を保証し、hostedテストは入力差し替え・環境更新・Viewの寿命を確認する。共有拡張・Keyboard・日本語IMEのOS連携は[実操作](ios-verification.md#製品の操作検証)で別に確認する。共通fixtureの合格を製品targetの合格へ読み替えない。

製品の実行評価はiOS 26.5 Simulatorとする。実機の触覚・熱・電力・ロック時保護・Handoff・ホストごとのKeyboard受理はこの範囲に含まれない。署名・アップロードとApple側の配信・実機での受け入れは[TestFlight手順](testflight.md)に分けて記録する。

複数scene、長時間利用、1 MB本文の入力追従は未確認条件として維持する。画面要素のラベル・座標だけではこれらの成立を証明しない。説明イラストは製品方針で同じ演出を表示する。発見性・片手操作・誤操作・復旧の理解は[UI評価課題](design/audit.md)で評価する。

性能判断には[測定手順](performance-verification.md)の条件・予算・適用限界を使い、対象ソースの測定値を`artifacts/`へ記録する。測定していない描画・電力・実機の性能を推定しない。
