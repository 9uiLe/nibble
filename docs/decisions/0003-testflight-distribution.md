# TestFlight配布と秘密情報の分離

## 状態と目的

- 判断日：2026-09-16。
- 状態：採用。専用ユーザーでの初回設定、Appleとの接続、署名・配布の実地確認は未実施。
- 対象：nibbleの内部TestFlight配布。最低対応OSは26.0、実機確認はiOS 26.5。

開発ユーザーで動くAIエージェントから配布作業を依頼でき、Appleの秘密情報をエージェントが直接参照できない構成にする。鍵・トークン・署名情報はGit管理しない。初回の受け手は本人の内部テスターとする。

## 選択肢

| 構成 | 評価 |
| --- | --- |
| 同じユーザーの無視ファイル・環境変数にAPI鍵を置く | Git除外はできるが、エージェントと同じ読取権限になるため不採用 |
| 同じユーザーでKeychainから取得する汎用スクリプト | Keychainのアクセス許可に依存し、汎用的な値取得をエージェントから隔離できないため不採用 |
| 別のMac・外部配布基盤 | 分離は可能だが、1台のMacによる運用という条件に対して初期負担が大きい |
| 同じMacの標準ユーザーを分離し、操作を限定したローカルサービスを使う | OSのユーザー境界を使い、日常の依頼は元のユーザーからできるため採用 |

## 構成と責務

開発ユーザーはコード編集、Nix検査、Simulator検証、署名なし実機archiveを担当する。配布ユーザーは、本人がレビューした固定commitのビルド、Xcode認証、署名、API鍵の保持、アップロードを担当する。

配布サービスには`status`と、private領域に準備したarchiveのhashを指定する`upload`だけを公開する。APIの任意パス、ファイルパス、コマンド、署名するデータを入力にしない。接続元UIDはOSから取得し、公開可能なbuild状態だけを返す。コード・設定・鍵・archiveをエージェントが書き換えられる領域に置かない。

ビルドは人が配布ユーザーで実行する。Swiftマクロやbuild scriptはMac上のコードを実行できるため、エージェントが変更するソースをサービスが取得・ビルドする機能は設けない。サービス更新と配布commitの選択は本人のレビューを境界にする。

## 運用と保守

- XcodeとApple SDKはローカルMacで管理する。GitHub ActionsはUbuntuの共通検査を担当し、署名・配布を行わない。
- JWTの生成はNixで固定した`cryptography`、署名・export・送信はAppleの`xcodebuild`を使う。独自の暗号実装やIPA upload protocolを保守しない。
- Team API keyはApple側では全アプリへの権限を持つ。サービスで対象アプリを固定し、鍵は配布ユーザー以外へ返さない。API照会は短い有効期限とGET scopeを用いる。
- 初期運用では配布ユーザーのターミナルでサービスを起動し、Fast User Switchingで通常ユーザーへ戻る。自動起動・遠隔接続・複数利用者対応は含めない。
- 出力を失った送信は再送せず、App Store Connectで確認する。処理完了とテスターへの配布は送信成功と区別する。
- TestFlight内部専用buildを使用する。外部配布には別buildと方針の見直しが必要になる。

専用ユーザーのhome権限、ACL、管理者権限を本人が維持する。root権限や配布ユーザーの認証をエージェントへ与えると、この境界は成立しない。初回に別ユーザー間の実際のアクセス制限とAppleの署名・送信を確認するまで、配布基盤の稼働完了とはしない。

製品のデータ形式、操作、描画処理は変更しない。配布ツールの変更からアプリの性能改善を主張しない。

## 見直し条件

複数の配布担当者、外部テスター、無人ビルド、OS自動起動、リモートからの依頼が必要になった場合は、権限とコード実行の境界を再設計する。Apple CLI/APIの仕様変更や鍵の失効時は、本人がprivate設定を更新し、まず限定された照会で接続を確認する。

具体的な設定・操作は[TestFlight手順](../testflight.md)、対象ソース・実測・未確認事項は[配布の検証記録](../testflight-validation.md)を参照する。
