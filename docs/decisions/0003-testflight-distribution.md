# ローカルMacからのTestFlight内部配布

## 状態と目的

- 判断日：2026-09-16。
- 状態：採用。Appleとの接続・署名・配布の実地確認状況は[検証記録](../testflight-validation.md)に記す。
- 対象：本人への内部TestFlight配布。最低対応OSは26.0、実機確認はiOS 26.5。

1台のMacと普段のmacOSユーザーで、検査・archive・署名・アップロードを繰り返せる構成にする。Appleの秘密情報をGitやエージェントへの出力に含めず、AIセッションからは限定した配布コマンドを実行できるようにする。

## 採用構成

`scripts/deploy-testflight.sh`を実行入口とし、Nixで固定したPythonからAppleの`xcodebuild`を呼ぶ。API認証、署名、export、アップロードはXcodeが担当する。独自JWT生成やアップロードprotocolを実装しない。

配布先は、本人1名を登録した内部グループ「本人用」とする。App Store ConnectでXcodeビルドの自動配信を有効にし、アップロードされた各buildを利用可能になり次第、同じグループへ配信する。スクリプトはアップロードまでを担当し、Apple側の処理・コンプライアンス・グループ配信・端末でのインストールは別の状態として確認する。

認証設定とAPI鍵は`~/.appstoreconnect/`、署名の秘密鍵は本人が管理するKeychainに置く。Pythonは変数の代入と任意の先頭`export`を解釈し、必須4項目だけを利用する。他の用途の追加変数は保持・出力・引き継ぎを行わない。鍵のパスをXcodeへ渡し、鍵の内容を読み込まない。設定をshellとして実行せず、ユーザー環境の認証用変数を子プロセスへ引き継がない。

| 担当 | 責務 |
| --- | --- |
| 本人 | Appleの契約・識別子・Capability・署名・API鍵の準備、保護されたログの確認、TestFlightのグループと端末での受け入れ |
| エージェント | ソースと配布コードの編集・検証、配布コマンドの実行、公開可能な結果の確認 |
| 配布スクリプト | cleanなcommitの記録、共通検査、固定依存でのarchive、メタデータ検査、Xcodeによる署名・送信、出力の限定 |
| App Store Connect | ビルドの処理、内部グループ「本人用」への自動配信 |
| GitHub Actions | Ubuntuで共通検査を実行。Appleの署名・配布は担当しない |

## アクセスと出力の契約

エージェントは秘密鍵・認証設定・Keychain・生ログを直接参照しない。リポジトリのAGENTS規約に加え、Claude Codeには対象パスのRead/Bash denyを設定する。配布スクリプトは設定ファイルの所有者・権限・形式を検査し、秘密情報や例外詳細を返さない。標準出力には工程、成否、version・buildのみを出す。認証設定の診断も、コードで定義した検査工程名と成否に限る。ファイルの存在・所有者・権限、設定や識別子の書式、鍵の配置規則を区別し、入力値や実際のパスを返さない。

同じOSユーザーのプロセスには同じ読取権限がある。deny設定は特定のエージェントに対する補助であり、任意のshell実行、エージェントによるコード変更、build scriptの実行をOSレベルで隔離しない。この限界を受け入れ、配布コード・マクロ・依存・build scriptは信頼するコードとしてレビューする。秘密情報への技術的なアクセス不能を保証する構成としては扱わない。

| 選択肢 | 判断 |
| --- | --- |
| 同一ユーザーの配布スクリプト、外部ファイル、出力制限、直接参照の禁止 | 採用。num-pathと共通の運用で、1台のMacから実行できる |
| 別OSユーザーと限定されたサービス | 強いアクセス分離に適する。アカウント・コード更新・サービスの保守が増えるため、現在の運用には採用しない |
| 別Macや外部配布環境 | 複数担当者・無人配布には候補となるが、現在の設備と初回配布の範囲を超える |

## 配布の契約

- 製品ソースと共有SPM lockはcommit済みかつcleanであることを要求する。archive後までcommitと作業ツリーを再確認する。
- iPhoneOS 26.5 SDKでReleaseをarchiveし、本体と共有拡張の識別子・version・build・最低OS・プライバシーリソースを検査する。Xcodeの署名・Apple側の受理をこのメタデータ検査で代用しない。
- 同一checkoutの配布を直列化し、build番号ごとの実行記録を上書きしない。結果不明の送信は自動再試行しない。
- DeveloperロールのAPI鍵を基本とし、本人がローカルの配布証明書・秘密鍵と両targetのprofileを事前に準備する。権限不足時にAPI鍵を自動昇格しない。
- Team API keyはApple側でアプリ1件だけに制限できない。スクリプトの対象固定が、Apple側の権限縮小になるとは扱わない。
- dry-runも署名・provisioning更新を伴う。アップロードは行わず、署名済みIPAの生成までを確認する。
- 内部専用buildを使用し、アップロード、Apple側の処理完了、内部グループへの追加、端末での利用成立を別々に確認する。

製品のUI・データ形式・描画処理は変更しない。配布ツールの変更から製品の性能改善を主張しない。

## 見直し条件

秘密情報の厳密な技術的隔離、複数担当者、外部テスター、無人配布、遠隔実行が必要になった場合は権限と実行環境を再設計する。Apple CLI/API仕様の変更や鍵の失効時は、本人が設定を更新し、設定確認とdry-runから検証する。

具体的な設定・操作は[TestFlight手順](../testflight.md)を参照する。
