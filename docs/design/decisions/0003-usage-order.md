# 使用回数順と長期間使っていない項目の補足

対象はS01一覧・S02検索、C05区分・C06保存済み行・C10コピー・C17回復。よく使う文章へ到達しやすくし、手動で整理する判断材料を項目の近くに置く。

## 利用と並び順

「使用」は本体アプリの一覧・検索から保存済み本文をコピーし、OSへの書込呼出しが戻ることを指す。貼付先での利用完了は意味しない。閲覧、編集、保存、共有取り込み、ピン操作、コピー前の失敗・取消は集計しない。編集画面の未保存本文コピーとキーボードのコピー・挿入は集計対象外とし、保存済み項目のUUIDで一覧・検索の利用を合算する。

すべて・ピン留め・検索は使用回数の降順、更新日時の降順、UUIDの昇順で並べる。SQLが対象全件を並べてから件数を制限する。追加取得は同じ順序の先頭から100件ずつ増やす。データが変わらなければ境界で重複・欠落せず、使用による順序変更では現在の取得範囲を読み直す。ピン留めは絞り込みであり、すべてをピン有無の区分に分けない。下書きは独立した区分、削除一覧は更新日時順とする。

## 永続化と失敗

SQLiteのschema version 2で`snippets`に非負の`use_count`とNULLを許す`last_used`を追加する。既存の全項目は0回・日時未設定とし、更新日時から履歴を推定しない。本文・タイトルの原文、UUID、ピン、削除状態、下書きは変更しない。移行は書込トランザクション内でversionを再確認し、異なる接続による移行の重複を避ける。

コピー完了ごとにUUIDの操作IDと完了日時を作り、`snippet_uses`への記録とカウンター更新を一つの書込トランザクションで確定する。同じID・対象・日時の再試行は更新せず成功とし、別内容によるID再利用を拒否する。遅い再試行で最終使用日時を過去へ戻さない。使用記録は本文の編集ではないため、revisionと更新日時を変えず、編集競合も起こさない。編集・ピン・削除・復元は使用履歴を保持し、完全削除は対応する操作IDも除く。

コピー済みなら呼出元タスクがキャンセルされても受理した記録を試みる。記録失敗時はコピー成功と区別した回復表示を残し、「使用記録を再試行」で同じ操作IDだけを送る。クリップボードへ再度書き込まない。再試行待ちの操作はモデルがメモリに保持するため、記録前のプロセス終了をまたぐ保証はない。OSクリップボードとSQLiteには共通トランザクションがなく、両者の確定を不可分にはできない。DBに確定した回数・日時は再起動後も保持する。

操作IDの保持量はコピー成功回数に比例する。重複判定を失わないため期限では削除しない。解析用の本文・端末情報は追加保存しない。将来保持方式を変える場合も、再試行による二重加算を防ぐ契約を守る。

キーボードはschema 1と2の既存DBを読み取り、本体の初回起動前にも使用できる。DB作成・移行は行わず、既存のピン優先順と権限契約を維持する。

## 整理候補

未削除の保存済み項目で最終使用日時があり、評価時刻との差が720時間以上なら「30日以上未使用」と最終使用日を行内に表示する。日付の表示には利用者の暦・localeを使い、候補の判定は経過時間で行う。ピン留めも含め、日時未設定・未来日時・下書き・削除済みは候補にしない。

一覧取得・再読込・アプリ復帰・コピー・削除・復元後の再取得で評価時刻を更新する。コピーで現在の日時が保存されると表示が消える。候補表示は判断材料であり、削除、取り消し、削除一覧からの復元、完全削除の確認を自動実行しない。

## 選択理由と評価

ピン優先の区分は固定した項目を見つけやすい一方、全件の使用回数順を分断するため採用しない。未使用項目だけの別画面や自動削除は管理操作・誤削除の負担が増えるため、既存行の控えめな補足と既存の整理操作を使う。回数だけの更新は重複再試行を識別できないため、操作IDの永続化を採用する。

順序とページ境界、複数接続、移行の原文保持、720時間の境界、記録失敗・再試行・キャンセルを自動テストする。小画面のライト／ダークでコピー後の順位と補足、検索、削除・復元を操作し、画像・動画で確認する。大量データの取得・コピー・スクロールは条件を固定して測定し、UI操作の待機時間と保存層の処理時間を分けて記録する。
