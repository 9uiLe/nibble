# タブの操作完了通知と削除の取り消し

状態：採用。判断日：2026-09-19。対象：S01・S02、C14・C18・C19、F06〜F08。[Issue #26](https://github.com/9uiLe/nibble/issues/26)の操作完了と回復を扱う。ユーザーの上部配置の選択に基づき、一覧・検索の通知を上部safe-areaバーへ統一する。

## 目的と構成

一覧と検索でコピー・削除・復元が成功したことを伝え、利用者が通知を閉じずに探索を続けられる構成とする。各NavigationStack内の上部`safeAreaBar`を使い、検索キーボードの有無で配置を変えない。作成ボタンは下部の独立した操作として残し、結果を同時に別の通知領域へ出さない。

| 成功した操作 | 結果文 | 対象名・操作 | 表示時間 |
| --- | --- | --- | --- |
| 本文のコピー | コピーしました | なし | 2秒 |
| 削除 | 削除しました | 保存層が確定した対象名・元に戻す | 6秒 |
| 通知からの復元 | 元に戻しました | 保存層が確定した対象名 | 2秒 |

通知は結果文と必要な対象名を左、取り消しボタンを右へ置く。対象名は1行で省略し、結果文と最小44 ptの操作領域を優先する。対象名の全文をアクセシビリティラベルと取り消しのヒントに含め、本文全体を通知へ載せない。バーは最小48 ptの高さを確保し、背景と画面内の配置はシステムに任せる。通知がない間は上部領域を解放する。

上部領域の出入りで一覧の内容は上下する。この負担を許容し、移動先を選ぶタブと作成ボタンの位置・幅を安定させる。通知の消去後はスクロール位置を復帰させ、検索語・入力フォーカスを失わないことを評価する。

「削除した項目」の復元・完全削除はシート内の通知を継続する。編集、共有拡張、入力エラーは各画面が担当する。失敗を成功通知へ変換せず、復元失敗は再試行、対象消失は再読み込みを提示する。完全削除の確認も独立して扱う。

## 状態、寿命と責務

`LibraryView`はタブの選択・シート・sceneの状態から通知を表示できる画面を決める。通知の配置層は該当するモデルの通知を表示し、常設の`LibraryResultFeedback`が成功の触覚を観測する。通知の有無でTabViewの構造やidentityを切り替えない。検索語・フォーカス・スクロール・編集の状態は既存の所有者が保持する。

`LibraryAccessoryContent`は通知表示と取り消し操作のUI境界を共用する。フォーカスの変化では通知の滞在を終えず、同じIDの期限を引き継ぐ。発生元と表示中のタブが一致しない通知は表示しない。

`LibraryModel.Notice`は通知ID、発生元（一覧・検索・削除シート）、結果文、対象名、復元対象UUIDを一つの値として持つ。新しい成功で置き換え、同じ文言でも異なるIDを発行する。`NoticeContext`は画面が通知を表示できる一回の滞在を識別する。UI所有者は操作の受理時、直接のasync呼出しは処理開始時にこの値を固定する。タブ移動、シート表示、sceneの非アクティブ化で滞在を終え、復帰時には別の滞在を開始する。以前の滞在で始まった処理は結果を永続化しても通知を再表示しない。

コピー・削除・復元は処理と結果反映までawaitできる。通知の期限を業務操作の完了に含めない。表示部品の`.task(id:)`で初めて期限を設定し、同じIDの再マウントで延長しない。期限後は現在のIDを照合して消去する。画面終了は通知を破棄し、確定済みのコピーや書込を取り消さない。

「元に戻す」は通知IDを渡す。モデルは現在の通知との一致を確認し、その通知に保存したUUIDだけを復元する。`LibraryTaskOwner`の重複抑止と、モデルの復元中UUID集合によって同じ対象の重複実行を防ぐ。処理中はボタンを無効にする。期限後の復旧は「削除した項目」が担当する。

読み上げと成功の触覚は、現在の滞在で受理した成功通知に一度だけ対応付ける。bodyの再評価や期限処理では再発生させない。シート内通知のopacityは既存の`Library.Notice` scopeが管理する。上部safe-areaバーの表示・消去と配置変化はOSに任せ、独自のopacity遷移を重ねない。

## OS対応と比較した案

最低対応はiOS 26.0。上部safe-areaバーを共通して使い、Tab Bar accessoryの有無を切り替えない。検索中に通知が隠れる[G13](../audit.md#g13-b--検索入力中の通知配置)と、一時通知でタブが動く[G14](../audit.md#g14-b--一時通知によるタブバーの再配置)を同じ配置で扱う。OSごとの実行条件と比較結果は[通知の検証記録](../../notice-validation.md)へ記す。

| 候補 | 利点 | 負担と判断 |
| --- | --- | --- |
| 上部safe-areaバー | 入力状態によらず同じ位置で結果を確認でき、タブと作成の操作位置を維持できる | 内容領域が上下する負担を許容して採用 |
| Tab Bar accessory | タブの結果を一か所へまとめ、標準の背景と配置を使える | 表示切替に伴うタブの再配置と検索入力中の非表示が、一時通知の目的に合わないため置き換える |
| 作成ボタンと同じsafe-area insetの通知 | シートと部品を共用しやすい | 作成と結果表示の配置責務が混ざる。一覧・検索では置き換える |
| 通知の有無でTabViewへmodifierを付け外す分岐 | APIの呼出しを限定できる | タブの構造的identityが変わり、入力やスクロールを失うため不採用 |
| 独自overlay | 配置を細かく調整できる | キーボード、タブバー、末尾の行の余白を独自に管理する負担が大きく不採用 |

## 評価条件と限界

通知の更新・期限の交差・発生元・遅延完了・復元対象・重複・失敗をテストする。Simulatorでは表示前・表示中・消去後、連続コピー、削除取り消し、検索入力中、タブ移動、シート開閉、バックグラウンド復帰を操作し、画像・録画・AXを照合する。小画面・長い対象名・ライトとダークで結果文、取り消し、末尾の項目を操作できることを確認する。

実行検証はリポジトリ規約に従いiOS 26.5だけで行う。26.0向けはdeployment targetとコンパイルを確認し、26.0実画面の評価とは区別する。VoiceOverの音声・触覚の体感、実機性能をAXやSimulatorだけで評価済みにしない。対象ソース、実施と未実施は[通知の検証記録](../../notice-validation.md)へ記載する。
