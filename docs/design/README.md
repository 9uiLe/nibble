# nibbleのUI設計

nibbleは、よく使うテキストを保存し、必要なときに探してコピーするiPhoneアプリである。利用者はコピーした本文を入力先のアプリへ貼り付け、作業を続ける。UIは、対象を見つける、内容を見分ける、操作結果を理解する、編集を安全に中断・再開する、という一連の行動を支える。

この文書はUIの目的、情報構造、設計資料の責務、設計と評価の手順を定義する。対象は日本語UIの本体と共有拡張。最低対応OSはiOS 26.0、実行評価はiOS 26.5 Simulatorとする。機能・保存・原文保持の契約は[製品設計](../decisions/0002-mvp-app.md)に定める。

## 用語と情報構造

| 用語 | 意味 | UIでの扱い |
| --- | --- | --- |
| スニペット | 保存済みのタイトルとプレーンテキスト本文 | 一覧と検索から選び、本文をコピーする |
| 下書き | 作成・編集の途中にある内容 | 保存済みとは別に保持し、再開または破棄する |
| 削除した項目 | 通常の利用対象から除いた保存済みスニペット | 専用の一覧から復元または完全削除する |
| タブ | アプリの作業領域を切り替える入口 | 一覧・設定・検索 |
| フィルター | 一つの一覧で表示する集合の選択 | すべて・ピン留め・下書き |
| シート | 呼出元の上で一つの作業を行う一時的な画面 | 編集、削除した項目の確認 |
| 操作領域 | タップや支援技術で操作を受け付ける範囲 | シンボルや背景の見た目とは別に確保する |
| セーフエリア | OSのバーや端末形状に妨げられない表示領域 | 本文と操作の配置に使う |

保存済みの利用、未完了の編集、削除からの復旧は異なる作業として構成する。同じデータを扱う画面でも、対象範囲と操作後の行き先を明確にする。

## 設計原則

| 優先する価値 | UIに求めること | 判断例 |
| --- | --- | --- |
| 内容と操作の安全性 | 対象と結果が分かり、入力を保持し、失敗から回復できる | 下書きの保持と保存済みへの確定を分ける |
| 利用可能性 | 文字サイズや入力方法が変わっても作業できる | 拡大時は内容の高さを増やし、操作領域を維持する |
| 目的への到達 | 探す・コピーする・入力先へ戻る流れを短くする | 項目を開かずに本文をコピーできる |
| 予測可能性 | 同じ意味には同じ名前・場所・振る舞いを使う | 標準検索、戻る、キーボードを使う |
| 読みやすさと製品の表情 | 内容の階層を保ち、装飾の強さを役割に合わせる | 文字の一覧面と浮く操作を分ける |

安全性と利用可能性を満たしたうえで、操作数、表示密度、視覚的な好ましさを比較する。利用頻度や配色の効果は、利用者の観測がない段階では設計仮説として扱う。

## 画面の構成

| 領域 | 主な目的 | 内容と操作 |
| --- | --- | --- |
| 一覧 | 見覚えのある内容を選ぶ | 集合の切替、下書き再開、編集、コピー、整理 |
| 検索 | 覚えている言葉から探す | 保存済みタイトル・本文の検索、結果の編集とコピー |
| 設定 | 操作環境を調整し、管理へ進む | 新規作成・コピーの左右設定、復旧、製品情報 |
| 編集 | 一つのテキストを作成・修正する | 任意タイトル、本文、保存、下書き保持・破棄 |
| 共有拡張 | 他アプリのテキストを取り込む | 受取内容の確認、共通編集、共有元への復帰 |

内容は縦方向に読み、対象選択は内容の前に、直接利用する操作は対象の近くに置く。標準のナビゲーション、検索、シート、入力部品を使い、色、情報の順序、内容の余白で製品の表情を作る。

識別子は、`F`が共通原則、`S`が画面、`C`が部品、`R`が根拠資料、`G`が監査課題を表す。同じ責務には同じIDを使う。Swiftの型の分割や改名によってIDを変える必要はない。

設計文書は採用する構成と評価基準を示す。実装がその基準を満たしているかは監査・実行記録で確認する。改善候補は採用まで監査記録に置き、製品仕様と区別する。

## 設計判断の記録

すべてのUI要素には、**目的、採用する構成、配置理由、代替案の利点と負担、評価条件**を記録する。色や余白のように複数画面で共有する判断は共通原則が所有し、個別画面から参照する。

| 根拠の種類 | 記録すること |
| --- | --- |
| 外部指針 | 発行主体、出典、適用する節、対象OSと用途の制約 |
| 製品判断 | 利用場面、選ぶ案、代替案とのトレードオフ |
| 仮説 | 期待する効果と、その期待を確かめる条件 |
| 観測 | 対象ソース、端末、データ、手順、結果、未実施条件 |

指針は候補を評価する根拠として使う。製品固有の数値や配置は、内容の識別性、操作のしやすさ、表示面積、保守負担を比較して決める。

## 設計・実装・評価の手順

```mermaid
flowchart LR
    A[利用場面と達成条件] --> B[画面構成と部品の責務]
    B --> C[根拠と候補の比較]
    C --> D[SwiftUIの実装・試作]
    D --> E[操作・外観・回復の評価]
    E --> F[仕様と検証記録]
```

1. **利用場面を定義する。** 利用者の目的、対象データ、操作後の復帰先を決める。入力中、待機、失敗、中断、復旧も状態として含める。
2. **画面と部品を割り当てる。** 現在地、対象の選択、内容、操作、結果の関係を構成図で示す。固定領域、スクロール、セーフエリア、読み上げ順を定める。
3. **候補を比較する。** 同じダミーデータ・文字サイズ・画面幅で設計上の差を評価する。情報の順序は構成図、タップ・入力・スクロール・素材の挙動はSwiftUIで確認する。
4. **責務に沿って実装する。** 同じ意味と振る舞いを持つ部品を共通化し、状態の所有者と操作の完了条件を定める。[実装規約](../library-policy.md)を適用する。
5. **評価して記録する。** [製品手順](../mvp.md)で操作と媒体を確認し、対象ソースに結び付ける。UIと同じ変更で設計資料を更新する。

情報構造、データ保護、操作の意味に関わる選択は判断記録を作る。契約内の寸法や表現の調整は部品台帳に理由と評価結果を残す。PRには対象IDと判断の要点、必要な画像・録画、実施範囲を記載する。

## 管理と保守

| 管理対象 | 正本・確認手段 | 理由 |
| --- | --- | --- |
| 設計の意味と判断 | Git内のMarkdown・Mermaid | コードと同じ変更単位でレビューできる |
| 実装値と状態の動作 | Swiftの製品コード | 実際に使う値と責務を一元化する |
| ネイティブの比較 | SwiftUIの試作・PreviewとSimulator | OSの文字、入力、ナビゲーションで評価できる |
| 実行結果 | 対象ソースを持つ検証記録 | 採用した設計と観測した結果を照合できる |
| 補助的な視覚検討 | 必要に応じたデザインツール | 複雑な案の比較に使い、採用結果を設計資料へ反映する |

SDKや主要OSを更新するときは、標準部品の挙動と関連する根拠を確認する。設計理由と網羅性はレビュー、文書と実装の未確認変更は共通検査、動作と見た目はローカルiOS検証が担当する。配布と秘密情報の扱いは[TestFlight手順](../testflight.md)に従う。

## 更新漏れの検出

[設計照合記録](review.json)は、見直したファイルのパスとSHA-256、設計への影響と判断の要約、確認した設計文書を保持する。SHA-256はファイル内容から計算する値であり、内容が変わると照合が不一致になる。対象一覧は検査コードが実ファイルから列挙し、記録側のファイル一覧で範囲を狭めることはできない。

| 検査対象 | 検出すること |
| --- | --- |
| `app/`の製品ソース・設定・アセット・依存lock | 追加、内容変更、削除、改名による設計影響の確認漏れ。新しいtargetも対象 |
| `docs/design/`、製品設計ADR、UI設計の一次資料 | 設計・根拠だけが更新された場合の照合漏れ |
| 共通原則・画面・部品・根拠・課題のID | 台帳の欠落、重複、未定義参照、範囲参照の途中の欠落、部品行の必須欄不足 |
| 照合記録 | 記録の欠落、不正な形式、空の判断要約、存在しない参照文書 |

`app/`内のMarkdown、名前が`Tests`で終わるディレクトリ、Xcodeの個人設定・生成物は対象から除く。設計照合記録自身も内容の照合から除き、形式と対象ファイル集合を検査する。除外規則と固定の文書入口は[検査コード](../../scripts/check_ui_design.py)が所有する。

共通の`documentation`検査がこの照合を必ず実行する。ローカルの`nix flake check`と、mainへのマージに必要なUbuntuの`workflow-policy`に同じ検査が含まれる。検査は読取専用であり、不一致を自動修復しない。

### 変更時の手順

1. 検査が示す追加・変更・削除ファイルから、影響する画面・部品・共通原則を特定する。
2. 実装と設計を照合し、仕様を変える場合は対応する文書を更新する。仕様を維持する場合は、変更理由と影響がないと判断した根拠を要約する。未解決事項は監査に残す。
3. 必要な実操作・テストを行い、対象ソースと条件を持つ検証記録へ結果を記す。
4. 確認した文書と判断の要約を指定し、照合記録の候補を作る。候補の差分を確認してから正本へ反映する。
5. 共通検査を実行し、実装・文書・照合記録を同じPRでレビューする。

以下は、画面・部品の照合を終えた後に候補を生成する形式である。`--summary`には実際の変更と判断を記す。参照文書は必要な数だけ指定する。

```sh
mkdir -p artifacts
nix develop --command python3 scripts/check_ui_design.py snapshot \
  --summary '実際に確認した設計への影響と判断' \
  --reference docs/design/screens.md \
  --reference docs/design/components.md \
  > artifacts/ui-design-review.json

diff -u docs/design/review.json artifacts/ui-design-review.json
```

差分を確認した後に反映し、再検査する。`diff`の終了コード1は差分があることを表す。

```sh
cp artifacts/ui-design-review.json docs/design/review.json
nix flake check --no-update-lock-file --print-build-logs
```

### 保証範囲

機械検査が保証するのは、記録した実装・文書との一致、IDと参照の構造である。意味のない文章や誤った設計理由、確認せず作り直した照合記録を判定する能力は持たない。レビューでは要約と実際の差分を照合し、配置理由と実操作の妥当性を確認する。

検査コード・対象範囲・CIを変更するPRには、その変更自体のレビューが必要である。外部指針の更新や利用者の行動変化はリポジトリ内のファイル差分として現れないため、SDK・主要OS・利用場面を見直す際に評価する。
