# nibbleのUI設計

nibbleは、よく使うテキストをiPhoneに保存し、探してコピーするアプリである。利用者はコピーした本文を入力先へ貼り付け、作業を続ける。UIは、対象を見つける、内容を見分ける、操作結果を理解する、編集を安全に中断・再開する行動を支える。

この文書は、本体と共有拡張の情報構造、設計資料の役割、実装と資料を照合する開発手順を定める。日本語UI、最低対応iOS 26.0、実行評価iOS 26.5 Simulatorを対象とする。保存と原文保持の契約は[製品設計](../decisions/0002-mvp-app.md)に定義する。

## 利用者の行動と画面

| 領域 | 目的 | 主な内容と操作 |
| --- | --- | --- |
| 一覧 | 見覚えのある内容から対象を選ぶ | すべて・ピン留め・下書きの切替、編集、コピー、整理 |
| 検索 | 覚えている言葉から対象を探す | 保存済みタイトル・本文の検索、結果の編集とコピー |
| 設定 | 操作環境を調整し、管理へ進む | 新規作成・コピーの左右設定、削除からの復旧、製品情報 |
| 編集 | 一つのテキストを作成・修正する | 任意タイトルと本文、保存、下書き保持・破棄 |
| 共有拡張 | 他アプリのテキストを取り込む | 受取内容の確認、共通編集、共有元への復帰 |

保存済みスニペット、編集中の下書き、削除からの復旧は、対象と終了条件が異なる作業として扱う。一覧・設定・検索はタブで作業領域を切り替え、一つの一覧の表示対象は上部フィルターで選ぶ。編集と削除した項目の確認は、呼出元の上で作業するシートを使う。

内容は縦方向に読み、対象選択は内容の前に、直接利用する操作は対象の近くに置く。標準のナビゲーション・検索・シート・入力部品に、製品の色、情報の順序、余白を組み合わせる。操作領域は見た目の記号サイズと分けて確保し、OSのバーや端末形状に妨げられないセーフエリアへ配置する。

## 設計の判断基準

| 優先する価値 | 求めること | 判断例 |
| --- | --- | --- |
| 内容と操作の安全性 | 対象と結果が分かり、入力を保持し、失敗から回復できる | 下書きの保持と保存済みへの確定を分ける |
| 利用可能性 | 文字サイズや入力方法が変わっても作業できる | 内容の高さを増やし、操作領域を維持する |
| 目的への到達 | 探す・コピーする・入力先へ戻る流れが短い | 項目を開かず本文をコピーできる |
| 予測可能性 | 同じ意味に同じ名前・場所・振る舞いを使う | 標準検索、戻る、キーボードを使う |
| 読みやすさと製品の表情 | 内容の階層を保ち、装飾の強さを役割へ合わせる | 文字の一覧面と浮く操作を分ける |

安全性と利用可能性を満たしたうえで、操作数、表示密度、視覚的な好ましさを比較する。利用頻度や配色の効果など、観測していない効果は設計仮説として記す。

## 設計資料と識別子

設計台帳は、共通原則・画面・部品などの責務と理由をID付きで記す文書である。IDは意味を識別し、Swiftの型名とは独立して扱う。

| 資料 | ID | 所有する情報 |
| --- | --- | --- |
| [共通原則](foundations.md) | F | 色、文字、寸法、余白、操作領域、状態表示、動き |
| [画面構成](screens.md) | S | 読み順、固定・スクロール、操作、終了と復帰 |
| [部品台帳](components.md) | C | 各要素の目的、構成、配置理由、代替案、評価条件 |
| [根拠資料](../../research/06-interface-design-evidence.md) | R | 外部指針、閲読範囲、製品への適用と限界 |
| [設計監査](audit.md) | G | 対象ソースの観測、不足、改善候補、未評価条件 |

情報構造や操作の意味を決める判断は、[判断記録](decision-template.md)へ候補・採否・理由を記す。台帳の契約内で行う調整は、その部品や共通原則へ理由を残す。設計文書は採用する構成と評価基準を定義し、監査・実行記録は対象実装が基準を満たすかを示す。改善候補は採用するまで監査で管理する。

根拠は、発行主体と適用条件を持つ外部指針、利用場面と制約に対する製品判断、期待する効果の仮説、対象ソースと条件を持つ観測に分ける。すべての要素に**目的・構成・配置理由・代替案の利点と負担・評価条件**を持たせる。

## 設計・実装・評価

[共通の設計手順](../../tools/ui-design/workflow.md)を使い、各段階でnibbleの次の条件を確認する。

| 段階 | nibbleで確認すること | 記録先 |
| --- | --- | --- |
| 利用場面 | 保存・探索・コピー・入力先への復帰、下書きによる中断と再開 | 画面構成、部品台帳 |
| 構成と比較 | 本文の識別、固定・スクロール、セーフエリア、キーボード、日本語、読み上げ順 | 共通原則、根拠資料、判断記録 |
| 試作・実装 | SwiftUIの標準部品、状態の所有者、操作の完了、入力保持と復旧 | 製品コード、[実装規約](../library-policy.md) |
| 評価 | 表示・操作・保存の成立、失敗と復旧、文字サイズ・外観・支援技術 | [製品手順](../mvp.md)に基づく検証記録 |
| 照合 | 採用仕様と実装の対応、未解決事項、変更の影響 | 設計台帳、監査、照合記録 |

情報の順序は構成図、iOS固有の入力・スクロール・素材はSwiftUIの試作とSimulatorで確認する。補助的なデザインツールを使う場合は比較目的を定め、採用結果を製品の台帳へ反映する。PRには対象ID、判断の要点、対象ソース、評価した条件を記載する。

## 設計基盤の構成

[共通ツールキット](../../tools/ui-design/README.md)は設計手順・ひな形・照合処理を提供する。nibbleは仕様と検査対象を所有し、次の接続を使う。

| 構成 | 責務 |
| --- | --- |
| [policy.json](policy.json) | 検査するパス、除外、ID体系、照合記録の保存先を指定する |
| [review.json](review.json) | 確認したファイルのSHA-256、判断要約、確認文書を保持する |
| [check_ui_design.py](../../scripts/check_ui_design.py) | nibbleのpolicyを選び、共通ツールの公開操作を呼ぶAdapter |
| [check_docs.py](../../scripts/check_docs.py) | 文書リンク・記載例・Skillを検査し、設計照合を必ず実行する |
| [flake.nix](../../flake.nix) | ローカルとUbuntu CIから同じ必須検査を実行する |

SHA-256はファイル内容を比較するための値である。照合記録と異なる内容が見つかった場合は、設計への影響を確認するまで検査が失敗する。共通ツールの配置と利用Interfaceは[ツールキットの契約](../../tools/ui-design/README.md#配置と配布の契約)に定める。nibbleの設定・台帳・照合記録はこのリポジトリで管理する。

## 更新漏れの検出

| 対象 | 検出すること |
| --- | --- |
| `app/`の製品ソース・設定・アセット・依存lock | 追加・変更・削除・改名による影響確認の漏れ。新しいtargetも対象 |
| `docs/design/`、製品設計ADR、根拠資料 | 設計や根拠を変更した際の実装照合の漏れ |
| 台帳とID参照 | 定義の欠落・重複、未定義参照、不正な範囲、部品行の必須欄不足 |
| 共通ツールキットと依存lock | 共通ルールや依存の変更による影響確認の漏れ |
| policyと照合記録 | 検査範囲の変更、記録の欠落・不正、空の判断要約、対象外の確認文書 |

対象ファイルはpolicyと実ファイルから列挙する。照合記録のファイル一覧を削っても検査範囲は狭まらない。policy自身も照合対象になる。ファイル内容の照合と製品のID参照の検査は対象を分け、共通ひな形のIDをnibbleの参照として扱わない。

`app/`内のMarkdown、名前が`Tests`で終わるディレクトリ、Xcodeの個人設定・生成物は対象から除く。照合記録自身はhashの入力から除き、形式と対象ファイル集合を検査する。具体的な範囲と除外はpolicyを正とする。

`nix flake check`の`documentation`が設計照合を実行する。mainへのマージにはUbuntuの`workflow-policy`成功が必要である。照合処理は読取専用で、CIによる記録の自動更新は行わない。

### 変更時の手順

1. 追加・変更・削除したファイルを、影響する画面・部品・共通原則へ対応させる。
2. 採用仕様と実装を照合する。仕様変更は台帳へ反映し、仕様を維持する場合も判断の根拠を要約する。未解決事項は監査に残す。
3. 必要な実操作・テストを行い、対象ソースと条件を持つ検証記録を作る。
4. 確認文書と判断要約から照合記録の候補を生成し、差分をレビューして反映する。
5. 共通検査を実行し、実装・設計・照合記録を同じPRでレビューする。

候補の生成は設計の承認を代行しない。`--summary`には実際の確認内容を記し、`--reference`には確認した文書を必要な数だけ指定する。

```sh
mkdir -p artifacts
nix develop --command python3 scripts/check_ui_design.py snapshot \
  --summary '対象の実装と設計を照合した判断の要約' \
  --reference docs/design/screens.md \
  --reference docs/design/components.md \
  > artifacts/ui-design-review.json

diff -u docs/design/review.json artifacts/ui-design-review.json
```

`diff`の終了コード1は差分があることを表す。判断要約・確認文書・ファイル一覧の差分をレビューし、採用した候補を反映して検査する。

```sh
cp artifacts/ui-design-review.json docs/design/review.json
nix flake check --no-update-lock-file --print-build-logs
```

## 検証と保守の責務

| 判断すること | 手段 |
| --- | --- |
| ファイルとIDの整合性 | 共通照合とnibbleへの接続テスト、必須CI |
| 理由・台帳の網羅性・根拠の適用 | 要約と実差分を使ったレビュー |
| 動作・見た目・アクセシビリティ | 対象環境の実操作、画像・録画、利用者評価 |
| 基盤の時間・メモリ・サイズ | 固定入力と対象実装を使う[基盤の測定記録](../ui-design-tooling-validation.md) |

意味のない文章や、確認せず再生成した照合記録を機械検査だけで判断することはできない。検査コード・範囲・CI自体の変更もレビュー対象とする。外部指針と利用者の行動は、SDK・主要OS・利用場面を見直す際に再評価する。配布と秘密情報の扱いは[TestFlight手順](../testflight.md)に従う。
