## 維持する構成

| 判断 | 維持する理由 | 妥当性の限界 |
| --- | --- | --- |
| 標準タブ・検索・keyboard | 領域の移動と入力をOSの期待へ合わせる | 設定タブが最適という利用者比較は未実施 |
| フィルターと独立した検索状態 | 同じ集合の表示変更と語句検索を混同させない | 対象の違いを初見で理解できるかは未評価 |
| 一つの一覧面と分離したコピー | 文字の比較と直接利用を両立する | 同名、長文、最大文字での識別には課題が残る |
| 保存済みと下書きの分離 | 入力を失わず、明示保存まで利用対象を変えない | 「閉じる」の意味と再開対象の見分けやすさを評価する |
| 削除と完全削除の分離 | 項目整理から回復できる | 連続削除や対象を含む確認には改善余地がある |
| 共通編集とネイティブ部品 | 本体と共有で同じ入力契約を維持し、運用を単純にする | システム部品を使っても全状態のUXは保証されない |

## 改善課題

優先度は利用頻度の実測順位ではない。**Aは操作の発見・識別・失敗からの回復、Bは適応と標準の期待、Cは密度や表現の比較**を表す。全件「提案・未実装」。実装の完了や使いやすさの改善は、対象の検証後に記録する。

### G01 A — 整理操作の可視入口

**確認した事実**：C11のピン・削除はcontextMenuとswipeActionsにあり、通常表示から押せる同じ操作の入口がない。編集の「その他」は本文共有と下書き破棄であり、保存済みのピン・削除の代替ではない。

**問題**：R08・R16が勧める、隠れたジェスチャー以外の操作へ十分つながらない。

**提案**：行の「その他」メニューと、項目を開いた画面での可視操作を比較する。第一候補は行のメニュー。コピーと本文の幅を奪いすぎる場合はアクセシビリティ文字サイズで縦配置へ切り替える。保存前の入力を整理操作で失わせる設計は避ける。

**確認条件**：説明なしでピン・削除へ到達できる。長押し・スワイプを使わずに同じ操作ができる。コピー誤タップと文字の識別性が悪化しない。現在の左右設定を保つ。

### G02 A — 複数の下書きを識別する情報

**確認した事実**：C07は全件に「下書きを再開」、無題に「編集中のスニペット」を表示する。`DraftSummary`はIDとタイトルだけを持つため、本文の異なる無題を表示から区別できない。

**提案**：主表示をタイトル、無題なら本文先頭から作り、補足として「下書き」を示す。DBから一覧用の短い要約だけを取得し、本文全体を行に保持しない。同じ先頭の場合の日時表示は追加候補とし、最初から情報を増やしすぎない。

**確認条件**：無題3件、同じタイトル、長文から意図した下書きを識別できる。再開は同じUUIDを使い、読み込みや保存の順序を変えない。本文全体の取得増加を避ける。

### G03 B — 大きな文字と操作対象の識別

**確認した事実**：コピー16 pt、新規作成18 ptは固定サイズ。ルートタイトルは1行・fixedSize、行は最大2行。復元ボタンの可視ラベルはアイコンのみで、カスタムの対象名付きラベルはない。

**問題**：R14の文字と意味のあるアイコンの拡大、R16の操作対象の明確化を全条件で満たすと判断できない。実際に欠ける・読めないとの断定はしていない。

**提案**：scaled metricまたはsemantic fontと、狭幅での行の組み替えを試す。復元は対象名を含む読み上げにする。タイトルを縮める前に標準タイトルや表示枠の選択を比較する。

**確認条件**：iOS 26.5で標準文字と最大アクセシビリティ文字、小さい対応iPhone幅、長い名前で、操作領域が重ならず内容を識別できる。VoiceOverで連続した復元ボタンの対象が分かる。

### G04 B — フィルター選択の視覚的な手掛かり

**確認した事実**：C04は文字・塗り・枠の色とselected traitで選択を表す。非選択と異なる記号や文言はない。

**提案**：選択項目にチェックを付け、選択以外の項目にも同じ記号幅を確保する案を比較する。標準segmented Pickerも同じ幅と文字条件で再評価する。

**確認条件**：色を区別しにくい表示でも選択を説明できる。切替でラベルが跳ねず、全フィルターに到達できる。選択traitと見た目が一致する。

### G05 A — 失敗の表示優先度と再試行の意味

**確認した事実**：空白検索ではC13がsnippetListの代わりになるため、List内のerrorとloadingは表示されない。C17の「再試行」はrefreshを実行し、コピー・ピン・削除などの失敗した操作そのものを再実行するわけではない。

**提案**：画面の状態を、失敗と必要な回復→読込→検索前案内→結果、の関係で明示する。失敗した操作と対象を保持し、再取得で回復するものと利用者が再操作するものを区別する。破壊的操作を自動再実行しない。

**確認条件**：空検索からの新規作成失敗、DB読込失敗、コピー失敗で理由が見える。再試行の文言と実行内容が一致し、検索語・下書き・UUIDを失わない。古い操作のエラーが新しい画面を上書きしない。

### G06 B — コントラストの実画面評価

**確認した事実**：F02の独自色はlight/darkで分岐するが、Increase Contrastを別途扱っていない。`.secondary`と独自背景、materialと背景の組み合わせを網羅して測定した記録はない。

**提案**：後述の単色計算を入口として、文字、ピン、コピー、選択、通知、エラーを実画面で確認する。基準未達の組み合わせだけ色・太さ・materialを調整する。

**確認条件**：light/darkとIncrease Contrast、Reduce Transparencyで読める。単色の合格をガラス全体へ一般化しない。本文4.5:1、意味を担うアイコン・状態3:1を目標に評価する。

### G07 B — 保存の可否と説明

**確認した事実**：C24は空白だけの本文で無効になる。本文ラベルは「本文」で、必要条件の明示はない。C31は下書き保持を説明する。

**提案**：本文が必要なことを入力の文脈で短く伝え、保存不可を色だけで表さない。入力直後から強いエラーを出す案は避け、未入力と保存失敗を分ける。

**確認条件**：新規作成でタイトルのみ、本文なし、空白・改行のみ、本文ありの違いを理解できる。原文の空白・改行の保持契約は変えない。

### G08 A — 削除・復元の対象

**確認した事実**：C19とC38の文言は「削除しました」「完全に削除しますか？」で、対象名を含まない。通常通知は新しい通知で置き換わり、直前の1件だけをUndoの対象にする。

**提案**：対象名を含む通知・確認を、長い名前でも操作が隠れない構成で試す。直前の復元と恒久的な削除一覧の役割を明確にする。汎用の複数段Undoを実装したと説明しない。

**確認条件**：2件連続で削除した後、どの項目を戻すか予測できる。期限後に両方を削除一覧から復元できる。完全削除は対象を確認して取消できる。

### G09 B — シート終了の例外

**確認した事実**：C20はinteractiveDismissDisabledを使用する。最新入力の永続化成功だけが閉じる、というデータ契約と、R09の標準スワイプ終了の期待に緊張がある。

**提案**：契約を維持したまま終了意思を受け取り保持を待つ方式と、明示終了を維持する方式を比較する。単に無効化を外して永続化前に閉じる変更は採用しない。

**確認条件**：日本語変換中、保持中、保存失敗、共有拡張、連続終了で入力を失わない。既存終了テストと実操作を両方確認する。

### G10 C — 主目的に対する密度

**確認した事実**：下書きは件数制限なく先頭へ表示される。初回・下書き0件では文言付き作成と下部＋の両方がある。設定は少ない項目を独立タブに持つ。

**提案**：下書きの先頭要約＋全件への入口、空状態での作成入口の一本化、設定の現行維持をそれぞれ別の比較にする。一度に全面変更しない。

**確認条件**：下書き0・3・20件と保存済み20件で、コピー対象への到達、再開の発見、説明を要した箇所を観察する。件数は試験条件であり典型ユーザー数ではない。

### G11 C — 操作と文言の一致

**確認した事実**：C23は本文末尾へ追記するがラベルは「本文にペースト」。C29の読み上げはkeep・discardも含め「保存中」。

**提案**：追記位置を予測できる表現、実行中の終了操作に合う状態説明へ合わせる。カーソル挿入へ変える場合は文言修正ではなく入力動作の変更として扱う。

**確認条件**：本文の途中を選択した状態でも挙動を予測できる。閉じる・破棄で保存済みの確定と誤認しない。読み上げと視覚表示が一致する。

### G12 B — 共有取込の待機

**確認した事実**：C41ではproviderの読み込みと下書き作成を待つ間、独自の進行表示や閉じる操作を配置していない。

**提案**：短い取込中表示と明示終了の入口を用意する。キャンセル時のprovider callback、下書き作成後の状態、共有元への通知を設計する。単にspinnerを足して完了扱いにしない。

**確認条件**：遅いprovider、非対応形式、取得失敗、キャンセル、共有元の終了で停止したように見えず、二重終了や不要な保存を起こさない。hostごとの条件を記録する。

## 単色のコントラスト計算

実施日：2026-09-17。対象は上記コミットの`NibbleTheme`のRGBと`LibraryScreen`のopacity。NixのPythonでsRGBの相対輝度を計算した。色の計算値であり、Screenshotからの測定ではない。

| 前景と背景 | light | dark |
| --- | --- | --- |
| accent / canvas | 6.0376:1 | 9.2667:1 |
| accent / コピー背景（accent 7%をcanvasへ合成） | 5.4432:1 | 8.2526:1 |
| accent / 選択背景（accent 14%をcanvasへ合成） | 4.8891:1 | 7.1391:1 |

各sRGB成分を`c <= 0.04045`なら`c / 12.92`、それ以外は`((c + 0.055) / 1.055)^2.4`へ変換し、`0.2126 R + 0.7152 G + 0.0722 B`を輝度とした。比は`(明るい輝度 + 0.05) / (暗い輝度 + 0.05)`。opacityは各sRGB成分を`前景 × alpha + 背景 × (1 - alpha)`として計算した。表示値のみ丸めている。

この6条件は4.5:1を超える。実際の色空間・合成、system secondary、エラー色、細線、ガラス、通知material、Increase Contrast、Reduce Transparencyは評価に含めていない。アプリ全体のアクセシビリティ合格とはしない。生の入力と結果は無視対象の`artifacts/design-research/solid-color-contrast.json`へ保存した。

## 実装へ進める単位

| 順序 | 単一の目的 | 対象 | 完了を判断する条件 |
| --- | --- | --- | --- |
| 1 | 対象を見分け、ジェスチャーに頼らず操作する | G01・G02・G08、C06・C07・C11・C19・C38 | 可視入口、対象名、同一UUID、取消・復元のシナリオを確認 |
| 2 | 失敗時に次の行動が分かる | G05・G07・G11、C17・C23〜C31 | 状態優先度、原因に合う回復、入力保持を確認 |
| 3 | 文字・視覚・入力の条件に適応する | G03・G04・G06、F02〜F06 | 同じデータで拡大・狭幅・外観・VoiceOverを確認 |
| 4 | 中断と外部からの取込を整える | G09・G12、S03・S07 | 永続化と終了の契約、遅延・取消・失敗を確認 |
| 5 | 日常操作の密度を比較する | G10 | レイアウト比較の結果で採否を決める |

これは改善の順序であり、全案の実装を既定にする計画ではない。実装前に同じ条件で候補を比較し、採用した案を台帳へ反映する。各変更は[判断記録](decision-template.md)と[検証手順](../mvp.md)へ接続する。

## 操作の評価方法

初見の利用者に操作方法を先に教えず、以下の目的を伝える。まず所有者本人の確認を使い、複数利用者の一般的な結果とは呼ばない。任意の外部送信やアクセス解析は追加しない。

| 課題 | 観測するもの |
| --- | --- |
| 見えている定型文をコピーして元の作業へ戻る | 対象の取り違え、不要な編集画面、復帰までの操作 |
| 本文だけ覚えている項目を探す | 検索開始、対象範囲の理解、0件からの回復 |
| 項目をピン留めする | 初回の到達、ジェスチャーの説明が必要か |
| 無題の下書きから目的の編集を再開する | 内容の識別、開き直し、入力保持 |
| 誤って削除した項目を戻す | 直後と通知消去後の復元先の発見 |
| 保存に失敗した入力を保持する | 原因の理解、次の操作、二重操作、内容の保持 |

開始・終了状態、誤操作、戻り、補助説明、本人の言葉を残す。時間を比べる場合は同じ条件を使い、試行順による学習も記録する。少数の観測へ統計的な改善率を付けない。製品性能の計測はこの利用者課題とは別に、[開発ガイド](../../CONTRIBUTING.md#性能の評価)に従う。

## この設計フェーズの完了条件

- 本体、編集、設定、復旧、共有、非アクティブ表示を台帳へ対応させる。
- 各要素に目的・配置理由・代替案・確認条件を記す。
- 外部指針と製品の選択、仮説、観測を区別する。
- 現行実装を正当化するだけで終えず、不足と比較すべき例外を記録する。
- 新しいUI判断を同じ形式で追加でき、既存の開発・PR・検証手順から到達できる。

このフェーズは設計と監査の成果物を作る。G01〜G12の製品コード修正、Simulator再検証、TestFlightの新規配布は含まない。実装後の各変更で確認する条件を具体化したものであり、アプリ全体のUI改善が完了したという申告ではない。

## 文書と共通検査の結果

2026-09-17、設計資料と開発手順の変更に対して`nix flake check --no-update-lock-file --print-build-logs`が成功した。実行環境はローカルMacのaarch64-darwin。文書検査は42 Markdown・476ローカルリンク・2 Swift例でエラーなし、Swift規約は31ソースで成功した。workflow、Nix書式、検証基盤の回帰テストは変更のない入力に対するNixの既存成功結果を再利用した。他の宣言済みplatformでの実行を申告するものではない。

`git diff --check`も成功。変更はMarkdownのみで、製品コード、設定値、テスト、外部依存、配布処理は変更していない。このためiOSのビルド・操作の再実行と新しいTestFlight配布は行っていない。設計監査の網羅性と判断理由は手動レビューで確認し、文書検査の保証範囲には含めない。
