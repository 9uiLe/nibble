## 採用レイアウトの操作と視覚確認

run `20260918T155157Z-keyboard-ui-c98d69`では、同じrunで製品をビルド・インストールし、VerificationAppの入力欄を使って操作した。本体で作成したダミー「受け取りの返信」を対象とし、タイトル・本文・「入力」が一つのButton、コピーが別のButtonであることをコードと画面へ照合した。

| 操作・表示 | 観測 |
| --- | --- |
| ライト／ダーク | 「入力」、タイトル、要約、ピン、コピーが重ならない。長い要約は省略して動作名を保持 |
| 「入力」からの挿入 | 保存済み本文が一度だけ入る。入力先で全選択・コピーした93 byteが原文とUTF-8完全一致 |

### 標準キーボードと表示条件

## 容量と性能

ソース`1839313261f4200e8502b8dd589c662cb4d2143d`の通常Releaseで、Simulator用`NibbleKeyboard.appex`は`du -sk`で1,596 KiBだった。arm64・x86_64の生成物であり、実機IPAやApp Storeのダウンロード容量を示さない。

表示・挿入・コピー・回転後、拡張プロセスのホスト側RSSは179,264 KiB（1回、稼働9分34秒）。Simulatorの共有frameworkなどを含む値で、ピークのphysical footprintや実機のメモリ上限への適合を示さない。

モデルが保持する要約50件、Readerの取得最大51件、利用時の本文1件、要求ごとの接続終了はコード上の契約である。速度・fps・hitch・初回表示・入力応答の改善を実測した結果ではない。性能評価は[手順](performance-verification.md)に従い、同じ入力先・端末・構成・データ・操作で行う必要がある。

キーボード非表示時は、Simulatorウィンドウのフォーカス取得と画像取得も失敗した。利用者の設定変更後に`sim-use keyboard-state`がhiddenからsoftへ変わったが、変更された設定名は確認していない。Command-Kの自動送信は終了コードが成功でも表示が変わらなかった。入力先のVerificationAppを開き直した後、採用レイアウトのrunで閉じる・入力欄タップによる非表示・再表示が成立した。環境の根本原因とショートカット自動操作の復旧は未確認である。

[AppleのSimulator解説](https://developer.apple.com/videos/play/wwdc2019/418/)にあるCommand-Kは、対象ウィンドウと実画面を照合して使う。VerificationAppは縦固定のため、横向きの評価にはSafariを使う。`keyboard-landscape.png`というファイル名だけで横向き成立と判定せず、実画面と入力先の条件を根拠にする。
