# UI設計と照合の手順

この手順は製品のUIを設計・変更する際に使う。製品固有の仕様と検査範囲は製品が所有し、共通ツールキットはIDとファイルの整合を検査する。

## 設計する

1. 利用者、場面、対象データ、作業の開始と完了を定める。
2. 画面・部品・共通原則へIDを付け、読み順、操作、遷移、入力・待機・失敗・復旧の責務を整理する。
3. 候補を同じ制約で比較し、採用理由、残る仮説、評価条件を記す。情報構造や操作の意味を決める場合は[判断記録](templates/decision.md)を使う。

外部の指針、APIの事実、製品の選択、効果の仮説、対象条件での観測を区別する。採用仕様は台帳、未解決の不足は監査、実験条件と結果は検証文書に置く。

## 評価して照合する

1. 対象ソース・設定・アセットと設計IDを対応させ、実装が仕様を満たすか確認する。
2. 必要な実操作・テストを行う。比較には同じデータ・環境・入力を使い、利用者の学習と試行順、対象ソース、観測と未実施条件を記録する。
3. 仕様を変える場合は理由とともに台帳へ反映する。維持する場合も照合の根拠を要約する。
4. 確認文書と判断要約を指定して照合記録の候補を生成し、差分をレビューして反映する。
5. ローカルと必須CIで`check`を実行する。policyの追加・除外もレビュー対象にする。

操作と設定形式は[Interface](README.md#interface)を参照する。機械検査は未確認の変更とID構造を扱い、理由の妥当性や使いやすさは判定しない。
