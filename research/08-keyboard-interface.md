# スニペットキーボードのUI設計研究

nibbleのキーボードは、入力中のアプリを離れずに保存済みの本文を見分け、直接挿入またはコピーする入力面である。この資料は、その背景・項目・フィルター・操作領域を比較するための一次資料と設計仮説をまとめる。製品の採用仕様は[キーボードの設計](../docs/decisions/0005-snippet-keyboard.md)、実行結果は[キーボードの検証](../docs/keyboard-validation.md)が所有する。

## 対象と確認方法

| 項目 | 条件 |
| --- | --- |
| 資料確認日 | 2026-09-18、ボタンの動作名は2026-09-19に再確認 |
| 対象 | 日本語のスニペット選択、直接挿入、個別コピー。文字入力キーの再実装は対象外 |
| OS | 最低iOS 26.0、実行評価iOS 26.5 Simulator |
| 外部資料 | Apple HIGの共通節・iOS/iPadOS節、UIKitの公式API文書。公開ページ本文を閲読 |
| 画面比較 | 既存run `20260918T140332Z-keyboard-ui-f0351c`の標準英語キーボードとnibbleのライト表示PNGを実際に閲覧 |
| 評価の限界 | 新しい案の利用者試験、誤タップ率、操作時間、実機性能は未測定 |

HIGは継続更新される。確認日のHIGとiOS 26.0のAPI availabilityを同一視しない。HIGの原則、APIの能力、特定条件の画面観測、製品への提案を以下で分ける。Appleが公開していないキーのRGB値・角丸・間隔を標準仕様として扱わない。

## 一次資料から確認できること

### 入力面の目的とOSとの境界

Appleは、固有の入力方法をシステム全体へ提供する用途をカスタムキーボードの対象とし、使える領域への適応と別のキーボードへの切替を求めている。設定・使い方の説明などは本体アプリへ置ける。キーボードに本体アプリの全機能を縮小して入れる必要はない。[Virtual keyboards](https://developer.apple.com/design/human-interface-guidelines/virtual-keyboards)、[Configuring a custom keyboard interface](https://developer.apple.com/documentation/uikit/configuring-a-custom-keyboard-interface)

HIGはキーボード内のヘルプ表示を避け、本体で使い方を説明するよう勧めている。常時表示の「タップして入力」という説明行を足す案より、ボタン自体に「入力」の動作名を持たせる案を優先する。権限操作の結果として必要な説明を返すことと、常設のチュートリアルは分ける。

`UIInputView.Style.keyboard`は、ぼかしと色調整でキーボード背景へ外観を合わせるAPIである。これは背景の契約であり、スニペット行の形・文字・配置を自動的に標準キーへ合わせるAPIではない。[UIInputView.Style.keyboard](https://developer.apple.com/documentation/uikit/uiinputview/style/keyboard)

`needsInputModeSwitchKey`がtrueなら切替キーを用意する。OS側の切替や音声入力ボタンと、製品側の操作を重複させない。[needsInputModeSwitchKey](https://developer.apple.com/documentation/uikit/uiinputviewcontroller/needsinputmodeswitchkey)、[Configuring a custom keyboard interface](https://developer.apple.com/documentation/uikit/configuring-a-custom-keyboard-interface)

### フィルターとナビゲーション

セグメントは、同じ対象・状態・表示へ作用する近い選択肢を一つにまとめ、選択状態を示す部品である。文字とアイコンを混在させず、短い名詞のラベルとそろった幅を使う。別のアプリ領域への移動にはタブバーを使う。[Segmented controls](https://developer.apple.com/design/human-interface-guidelines/segmented-controls)

**適用**：「すべて／ピン留め」は同じスニペット集合の絞り込みなので、単一選択のセグメントが候補になる。「更新」を3番目のセグメントへ入れない。チェックマークやページ遷移の矢印を選択状態へ追加する必要はない。具体的な幅と高さは可読性と占有面積から決める製品判断である。

### 文字を見分ける行と実行ボタン

文字中心の情報は、一列の行で読み比べやすい。行の内容は簡潔にし、狭い幅でも識別に必要な情報を残す。選択後には、その行が何をしたかに合ったフィードバックを返す。[Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)

ボタンは直ちに行う操作を表す。HIGは、記号より明確に伝えられる場合に短い動作名の文字を使うことを勧めている。押した状態を用意し、隣の部品と見分けられる空間を取る。一般的な44×44 ptの操作領域は記号自体のサイズとは異なる。何個もの操作を同じ強い色で目立たせると、優先する操作が分かりにくくなる。[Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)

**適用**：スニペットを一列に並べて識別の横幅を保つ。その行は詳細への移動ではなく即時挿入なので、タップ可能な面と押下状態を示す。入力キーには「入力」と短く動作を表示する。タイトルや本文は対象を説明する文字であり、ボタンの結果を説明するラベルとは区別する。内容と動作名は同じ操作領域に含め、コピーは別の実行対象として分離する。詳細表示を意味する開示矢印を挿入の説明に転用しない。

### 階層、余白、固定操作

整列・余白・背景形状・区切り線は、関連するものをまとめ、異なる役割を分ける手段である。重要な内容の面積を、補助情報で圧迫しない。操作は機能と頻度でまとめ、無関係な操作を密着させない。[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)

**適用**：絞り込み、挿入対象、入力面の終了・ページ移動を三つの領域として整理する。更新・製品名・ページ番号は入力対象より弱い階層にする。狭いキーボードでは、上下のバーを増やすより、既存の領域で関連する操作をまとめる。これは高さと識別性の調整であり、操作回数が減るという実測結果ではない。

### 色、素材、文字の役割

Appleは、同じ色に異なる意味を持たせず、外観に適応するシステム色を使うことを勧めている。`label`と`secondaryLabel`は主情報・補足情報、`separator`は境界という意味を持つ。背景色の名前は階層を表すため、見かけの灰色だけを理由に選ばない。[Color](https://developer.apple.com/design/human-interface-guidelines/color)、[Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)

Liquid Glassは内容の上にある操作・ナビゲーションの層に使い、内容面へ重ねすぎない。標準部品は必要な外観を取り込むため、全行へ独自のガラス効果を足す理由にはならない。[Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

文字の重要度はサイズ・太さ・色で示し、少数の文字スタイルを使う。SF Symbolsは隣の文字と太さ・大きさをそろえられる。[Typography](https://developer.apple.com/design/human-interface-guidelines/typography)

**適用**：背景は入力面の連続性、行の面は実行対象、主文字はスニペットの識別、補助文字は本文の確認に使う。全行にブランド色を塗らない。ピンは属性であり、実行ボタンと同じ強さにしない。権限不足を薄色だけで表さず、記号と説明を併用する。製品の[表示方針](../docs/design/decisions/0002-fixed-interface.md)は維持する。

採用する`tertiarySystemBackground`はsecondary背景上の内容に使う公開の階層色である。入力面に重なるキーへ割り当てる判断は製品側で行い、keyboard専用色のAPIとは扱わない。ライト／ダークのキーとOS背景の分離は実表示で確認する。[tertiarySystemBackground](https://developer.apple.com/documentation/uikit/uicolor/tertiarysystembackground)

### 権限の意味を保つ

AppleはFull Accessなしでも本体の共有コンテナを読み取れること、Full Accessの有効化には明示的な利用者操作が必要なことを説明している。[Configuring open access for a custom keyboard](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard)

**適用**：nibbleの直接挿入とコピーは既存の契約どおり区別する。コピー権限の案内は副操作に属し、権限がないことをキーボード全体の故障のように見せない。コピーの条件と原文の扱いは[製品設計](../docs/decisions/0005-snippet-keyboard.md)を正とする。

## 既存画面の観測と改善仮説

比較したのは、同じiPhone 17 Pro / iOS 26.5 Simulatorのライト表示である。標準英語キーボードは、灰色の入力面から明るいキーの面を分け、キー間の隙間で操作単位を示していた。nibbleは同じ入力面の上へ、区切り線付きのタイトル・要約・鍵付きコピー記号を配置していた。これは二つのPNGで確認した構成であり、Appleの設計意図や全端末での仕様を断定するものではない。

| 確認できた構成 | 改善仮説 | 評価すること |
| --- | --- | --- |
| nibbleの行は背景と同じ面にあり、コピー記号だけが明示的な操作に見える | 挿入する行へ独立した面と押下状態を付けると、主操作が識別しやすい | 行とコピーが別操作だと分かるか。押下中・成功・失敗の違い |
| ピン付き行ではタイトルの左にピン、要約は行の左端にある | 属性を主文字より弱くし、タイトルと要約の始点をそろえると読み比べやすい | ピンの有無が混じった一覧で文字の位置が動かないか |
| フィルターが最大260 pt、更新が右端にあり、幅により間が大きく空く | 操作領域の余白を規則化するとフィルターと項目の対応が明確になる | 縦・横・狭い幅で不自然な空きや文字切れがないか |
| 1ページだけでも前後の無効矢印・番号が表示される | ページ移動がない状態の補助表示を簡素にすると対象が目立つ | 複数ページの発見可能性、読み込み中に配置が飛ばないか |

上記は見た目とコードに基づく仮説であり、誤操作や応答時間の実測ではない。ページ表示の変更は挙動と状態遷移へ影響するため、配色だけの変更と分けて評価する。

## 比較する構成

| 構成 | 利点 | 負担 | 判断 |
| --- | --- | --- | --- |
| 一面の区切り線付きリスト＋セグメント | 文字の横幅と表示密度を保ちやすい。標準の一覧に近い | 入力キーとしての面が弱く、コピーと行タップの関係を別に示す必要がある | 読み取り中心なら有力。即時挿入を主操作とする本用途では改善余地 |
| 一列の入力キー状の行＋独立したコピー＋セグメント | タイトルと要約の横幅を保ち、挿入・コピーを面で区別できる。標準キーボードの操作単位と対応を作れる | 行間・面が一覧より面積を使う。独自の押下状態と配色の確認が必要 | **試作の第一候補**。狭い外周余白、そろった行間、控えめな角丸で密度を維持 |
| 二列以上のタイル＋アイコンのカテゴリバー | 短い定型語を位置で覚える用途には向く | 長い日本語タイトルや似た内容の区別、コピーの独立領域が窮屈。保存順の変化で空間記憶が崩れる | 現在の任意長スニペットには不採用。短いラベルを前提にする別要件が必要 |

推奨案の「キー状」は文字キーの複製を意味しない。本文の識別に必要な一列の情報構造を保ち、即時挿入の対象であることを面・間隔・押下表示で伝えるという製品判断である。標準のセグメントと背景APIはそのまま利用できる。

## 試作で確かめる具体条件

1. **主操作**：タイトルと要約を持つ行の面が挿入、独立したコピー領域がコピーだと識別できる。二つのタップ領域が重ならず、押下状態が見える。
2. **寸法**：補助ボタンは44 ptの操作領域を維持し、アイコンだけ小さくできる。外周・行間・内部余白は役割別に少数の値へまとめる。値はAppleの指定値とせず、縦288 pt・横196 ptの現行入力面で評価する。
3. **情報量**：タイトルと本文の始点をそろえ、ピンの有無で動かさない。長い日本語・同じ先頭のタイトル・空タイトル・絵文字を混ぜ、コピー領域の侵食と切れ方を確認する。
4. **色**：ライトとダークで背景・入力対象・押下中・選択フィルター・無効操作が区別できる。キー用に製品独自の色を定義する場合は明暗の値と役割を記録し、「OS標準キー色」と呼ばない。
5. **密度**：表示できる行数だけを最大化せず、フィルター、対象、補助操作の区別を保つ。コピー案内が出ても主操作を失わず、スクロール領域が残る。
6. **既存契約**：全件／ピン留め、空、読み込み、失敗、複数ページ、Full Accessの有無、入力先変更を確認する。表示の変更によって直接挿入とコピーのガード条件を変えない。

背景・セグメントの標準API使用だけでデザイン全体の妥当性を判断しない。画面と録画で操作と見た目を評価し、採用した値・代替案・未確認事項を製品台帳と検証記録へ反映する。
