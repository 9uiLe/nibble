# 未決定事項と検証計画

整理日：**2026-09-13**。対象：**iOS 26.0 以上**。01〜04 の調査を、次の実装・設計判断へつなぐための計画である。以下の実験は**すべて未実施**であり、採用済みの構成や測定結果ではない。

## まず決める製品上の問い

| 問い | 比較する選択肢 | 判断に必要な情報 |
| --- | --- | --- |
| 最初に解決する利用場面は何か | メッセージの定型文、メール、Web フォーム、コード等 | 実際に使う入力先、頻度、短文／長文、片手利用、既存の手順で困る点 |
| 「利用完了」はどこか | コピー完了、相手欄への挿入・ペースト、元の作業への復帰 | 利用者の目的に合う終点。コピー成功だけで挿入成功とは扱わない |
| 何をスニペットとして保存するか | plain text、書式付き、画像・ファイル、変数展開 | 原文維持、検索、共有形式、サイズと編集部品への影響 |
| 何から呼び出すか | 本体、Shortcuts / Controls、Share / Action、Keyboard、Widget | 対象シーンでの成功率と、初期設定・切り替え・保守の負担 |
| どう探すか | 本文／タイトル検索、固定項目、最近使った項目、分類 | 思い出せる情報、件数、日本語の短い検索、並び順の安定性 |
| どのように編集・削除を確定するか | 明示保存／自動保存、Undo／復元、下書き | 中断・保存失敗・誤削除から回復する体験とデータ保持 |
| 何を機密として守るか | 全項目同じ扱い／機密項目を区別 | ロック画面・キーボード・システム検索・コピー・export の露出範囲 |
| 同期は初期版に必要か | 端末内のみ／任意の端末間同期 | 複数端末の具体的な需要、アカウントと競合対応の運用負担 |

これらは質問票をすべて埋めるまで開発を止める条件ではない。未回答の部分には仮定を記録し、次の最小実験で検証する。ただし、機密性や保存結果を利用者へ約束する前に、その意味と保証範囲を決める。

## 検証の順序

**推奨する進め方：** V0 で対象シーンを絞り、V1 の基準を作る。V2 で価値のある入口を選び、その権限とプロセス構成を V3 の保存方式比較へ渡す。V4〜V6 は最初の縦通しの試作から並行して確認する。V7 は同期の必要性が確認できた場合だけ進め、配布前に V8 を行う。

| ID / 順序 | 確かめる問い | 最小の実験と条件 | 残す証拠・判断すること | 根拠 |
| --- | --- | --- | --- | --- |
| **V0：利用場面** | どの往復を短くすると価値があるか | 代表的な入力先を 2〜3 個選び、ダミーの定型文を現在の方法で利用する。初回設定と日常の利用を分け、作成・修正・誤削除からの復帰も観察する | タスク定義、操作列、総完了時間、迷い・失敗。初期版で解く場面と「利用完了」の終点 | [01](01-invocation-and-platform.md)、[03](03-ux-and-performance.md) |
| **V1：基本の往復** | 本体だけで気持ちよく作成・検索・コピー・復帰できるか | 本体でローカル CRUD と検索・コピーを通し、Notes / Safari 等の選んだ欄へ利用者がペーストする。空・少量・長文、cold / warm、オフライン、日本語変換、保存失敗を確認する | 動画、画面、区間別の測定値、本文一致、保存失敗時の下書き。追加導線を比較する基準と最初の性能予算案 | [02](02-data-and-architecture.md)、[03](03-ux-and-performance.md) |
| **V2：追加の入口** | 設定と切り替えの負担を含めても V1 より役立つか | 選んだシーンに合う入口を一つずつ試す。Shortcuts / Control の一覧・作成、Share / Action の取り込み、Full Access なし Keyboard の挿入を候補とする。未起動、ロック、権限拒否、非対応 host・入力型、削除済み ID、元の日本語キーボードへの復帰を確認する | host・入力欄ごとの成否、設定手順、成功率、往復時間と誤り。初期版の入口と必要な権限。失敗時の代替手順 | [01](01-invocation-and-platform.md)、[04](04-security-distribution-and-operations.md) |
| **V3：保存と共有** | 必要な入口でデータの新しさ・保存・移行を保てるか | SwiftData を含む候補を同じデータと操作で比較する。本体と extension の同時利用、更新直後の再表示、保存中の終了、履歴 token 失効を試す。Keyboard を選ぶなら read-only での DB 初期化と、版付き snapshot の公開・切り替えを比較する | 成功した保存と再読取の対応、競合・回復記録、初期化時間、メモリ、必要なコードと依存。保存方式、変更通知、共有の責務 | [02](02-data-and-architecture.md) |
| **V4：日本語と検索** | 原文を変えず、想定した結果を入力に追従して出せるか | 正規化・表記揺れの期待結果を先に記す。1〜2 文字、結合濁点、半角カナ、絵文字、記号・改行を含める。変換途中の入力、連続検索、古い結果の遅着、更新・削除・import 後の index を確認する | 期待／実際の検索結果、コピー・export 後の本文一致、入力動画、検索と描画の測定。検索仕様、index の必要性、世代管理 | [02](02-data-and-architecture.md)、[03](03-ux-and-performance.md) |
| **V5：保護と復旧** | 失敗・ロック・更新で内容を失ったり想定外に露出したりしないか | ロック後・再起動直後に採用入口を呼び、本文表示と認証を確認する。アプリ切替 snapshot・ログ・検索公開範囲を点検する。旧データから移行し、途中失敗・export/import・誤削除から回復する。期限付きコピー A の後に別アプリで B をコピーし、A の期限後も B が残るか確認する | 各状態で読める／操作できる範囲、回復前後のデータ比較、ダミー内容による画面証跡。保護属性、認証、コピー期限、移行・復元方針 | [01](01-invocation-and-platform.md)、[02](02-data-and-architecture.md)、[04](04-security-distribution-and-operations.md) |
| **V6：使いやすさと性能** | 主要タスクを支援技術でも完了でき、遅延が誤操作を増やさないか | 同じ試作で小さい画面、最大 Dynamic Type、VoiceOver、片手、外付けキーボード、外観・動きの設定を確認する。実機 Release で起動・検索・保存・スクロールと連続利用を測る | 完了率、誤り、再試行、総時間、hitch・メモリの記録、Instruments trace。操作領域、配置、通知、更新範囲と性能予算 | [03](03-ux-and-performance.md) |
| **V7：任意の同期** | 同期の便益が競合と運用負担に見合うか | 採用を検討する場合のみ、2 端末でオフライン編集、同時編集、削除対編集、長期不在、アカウント変更、同期の無効化・再開を試す。V1 の操作を通信待ちにしない | 競合した本文の保持、両端末の収束、アカウント別データの分離、回復手順。同期の要否と方式。即時同期を前提にしない UI | [02](02-data-and-architecture.md)、[04](04-security-distribution-and-operations.md) |
| **V8：配布と更新** | 初期設定・移行・プライバシーを含め配布可能か | 実在する target で archive と検証を行い、選んだ配布方法で更新を試す。Keyboard を含む場合は入力機能・切替・Full Access 不要の動作を確認する。manifest、SDK、privacy policy、依存 license、サポート先を点検する | 配布物、更新結果、審査担当者向け手順、宣言内容の対応表。初期リリース範囲と保守担当。自動検証成功を審査承認とは扱わない | [04](04-security-distribution-and-operations.md) |

一つの試作に全候補を組み込まない。例えば Keyboard を使う場面が見つからなければ、そのためだけの保存共有や設定 UI を初期版へ追加しない。候補を外した理由も、対象シーンと証拠に結び付けて残す。

## 共通の実施条件と証跡

### 実装・OS・データ

- 実在する本体・extension の deployment target を **26.0** にそろえる。選んだ Xcode・Swift language mode・isolation 設定・SDK と、使う型／member の availability を記録する。
- iOS 26.0 と採用 Xcode が対応する最新の正式版 iOS で影響範囲を確認する。環境を用意できない場合は、その条件を未実施と明記する。
- OS 連携は実際の host と入力欄を記録する。アプリ本体で成功したことを extension の成功とみなさない。Full Access、ロック、Handoff、言語、Action Button 対応の有無も残す。
- 共通データの初期案は **0・20・1,000・10,000 件**。件数は比較のための仮定で、製品の上限や利用実態ではない。本文の長さ・文字構成・検索結果件数もそろえ、必要に応じて仮定を更新する。
- 実データ、秘密情報、第三者の入力文を証跡に使わない。画面と復旧の検証には再生成可能なダミーデータを使う。

### 時間・正しさ・体験

**呼び出し操作 → 選択可能 → コピー／挿入完了 → 元の作業を再開**の区間を分ける。初回設定時間と日常操作、利用者の探索時間とアプリの処理時間も別に残す。検索や保存が速くても、誤った本文や古い結果を出す状態は成功にしない。

性能は同じ実機・OS・Release 構成・データ・操作で比較する。測定回数、cold / warm、熱・電源状態、集計方法を残す。[03 の測定案](03-ux-and-performance.md)を開始点にするが、原著の係数、Apple の大まかな時間目安、少数試行の最大値をそのまま製品保証へ転用しない。

UI/UX は対象コミット・端末・OS・到達手順を付けたスクリーンショットと画面録画で確認し、変更時は PR に閲覧可能な形で添付する。性能の改善を主張する場合は対応する測定値も添える。録画だけでは処理時間や原因の証明にならない。

### ローカルとクラウド

iOS ビルド、SDK 統合、権限、UI、性能、署名・配布はローカル Mac / Xcode / Simulator / 実機が担当する。Ubuntu CI は補助ツールの静的検査を担当し、macOS runner は使用しない。補助ツールを追加する場合は Nix に宣言・固定し、[開発ガイド](../CONTRIBUTING.md)に従う。今はアプリと scheme がないため、将来の build コマンドを推測で記載しない。

## ADR に進める条件

候補の API が存在するだけでは採用を決めない。選んだ利用場面で動くこと、iOS 26.0 と必要な extension・権限で使えること、入力と保存の正しさ、実測に基づく性能、保守・復旧の負担を比較できる状態にする。

後から変更しにくい判断は、初期導線、保存・共有方式、検索規則、保護と認証、同期、主要依存の単位で記録する。すべてを一度に確定する必要はない。未確認を残して提案する場合は何を確かめれば採用できるかを明記し、採用済みとして扱わない。

この調査時点で決定済みなのは、プロジェクトの価値、iOS 26.0 以上、Nix の補助ツール管理、ローカルと Ubuntu CI の責務、UI 証跡と PR のルールである。SwiftUI / UIKit、SwiftData / Core Data / SQLite、各 extension、同期・アカウント・AI・課金は未決定である。
