# 製品設計の研究資料

nibbleは、作業中に必要なスニペットを素早く呼び出し、作成・編集・削除を少ない操作で行うiOS向けツールである。このディレクトリは、使いやすさ、原文の保持、描画・応答性能、保守・復旧を判断するための一次資料、比較条件、検証結果を管理する。

最低対応OSは**iOS 26.0**、実行検証は**iOS 26.5のみ**。26.0への適合はdeployment targetと個別APIのavailabilityで確認する。一次資料と実行結果の確認日は2026-09-13とする。

## 設計と検証の構成

| 対象 | 役割 | 定義・手順 |
| --- | --- | --- |
| 開発規約 | 製品の価値基準、Nix依存、ローカルとCIの責務、PRの証跡要件を定める | [開発ガイド](../CONTRIBUTING.md) |
| 検証基盤 | Apple CLIによるビルド・実行管理・撮影と、sim-useによる画面読取・操作を組み合わせる | [設計](../docs/decisions/0001-local-ios-verification.md)、[共通コマンド](../docs/ios-verification.md) |
| VerificationApp | 検証コマンド・文字列照合・撮影の成立を試験するfixture | [project設定](../validation/project.json) |
| ResearchProbe | 保存方式3案、検索、復旧、本文編集、コピー、OS連携を比較する研究用アプリ | [構成と実行手順](../validation/RESEARCH.md) |
| 製品の評価 | 利用場面に対して入口・データ・表示・保護・同期・配布を選ぶ | [V0〜V8の検証計画](05-decisions-and-validation.md) |

ResearchProbeの画面は比較用のUIKit実装であり、保存方式比較にはSwiftData・Core Data・SQLiteを使う。製品のUI・保存・共有・呼び出し・同期は採用判断の対象とする。基盤や比較用アプリの成功は、評価していない製品条件の合格を意味しない。

## 設計判断に使う知見

| 領域 | 根拠と設計への意味 |
| --- | --- |
| 呼び出し | 呼び出し・取り込み・他アプリへの挿入は異なる能力である。任意画面への重ね合わせや全入力欄への直接挿入を前提にせず、hostと入口の組み合わせを評価する。[01](01-invocation-and-platform.md) |
| 共有 | AppleはFull AccessなしKeyboardの共有領域のread-only利用を説明する。DB初期化・sidecar・移行・更新反映の成立には、実際のextensionでの確認が必要。[02](02-data-and-architecture.md)、P04 |
| 保存 | 3保存方式の基本CRUD・再読込は成立する。移行・プロセス間共有・実機性能の条件を満たす方式を選ぶ。live WALを欠くDB本体だけのcopyをbackupにしない。E01〜E09 |
| 日本語検索 | 保存原文と検索用表現を分ける。trigram MATCHでは1〜2文字の日本語検索が一致しないため、短い検索を満たす方式を比較する。E10〜E12 |
| 操作と表示 | コピー完了に加え、元の作業の再開までを評価する。比較用の縦配置は、小画面・最大文字サイズ・キーボード併用で本文が切れるため製品への採用条件を満たさない。E24、[03](03-ux-and-performance.md) |
| システム連携 | Shortcutsの一覧への登録と実行成功は別の条件である。ResearchProbeの前景アクションは実行失敗を観測しており、原因は未特定。E25 |
| 保護と運用 | Data Protection、ロック、コピー、同期で保護範囲が異なる。コピー期限は他アプリに保存した内容を回収しない。配布物のAPI・SDK・データフローから宣言を確定する。[04](04-security-distribution-and-operations.md) |
| 性能 | Simulatorの計測値は比較試作の観測値である。実機で起動・入力・検索・保存・hitch・メモリを測り、性能予算を決める。MetricKitも個別APIのavailabilityと実配送を確認する。[03](03-ux-and-performance.md) |

## 評価状態と採用条件

[iOS 26.5の実行結果](experiments/ios-26-5-validation.md)は、保存・検索・移行・復旧・画面操作の成立と失敗を条件ごとに示す。実extension、実機性能・ロック時の保護、同期、署名配布、利用者・支援技術による評価は未完了である。KLMとJotaの原著本文は未取得のため、係数や効果量を設計根拠に使わない。

製品の入口・対象host・保存と共有方式・検索規則・画面構成・機密項目・性能予算・同期・配布運用は、評価結果を基に決定する。評価用の基礎データはテキストとし、rich text、画像・ファイル、変数展開、アカウント、AI、課金は便益と保守運用を比較する判断項目とする。

## 根拠と更新の規則

- **事実**は公式API文書、WWDC transcript、言語・SQLite等の一次資料、原著論文で確認した内容を指す。
- **設計への示唆・推奨**は事実をnibbleの目的へ適用する候補であり、採用決定には対象シーンの検証が必要となる。
- **観測結果**は記録した端末・OS・ソース・データ・権限の条件に限って解釈する。
- **未確認・未決定**は追加の実験または製品判断を必要とする条件として明示する。

各資料台帳にURL、著者・発行主体、日付、閲読範囲、適用限界を記す。DocCの公式JSON本文とmetadata、動画のtranscriptと視聴、書誌と原著本文を区別する。外部の文書全文を転載せず、要約・分析・出典をGitで管理する。

生成ログ・画像・動画はGit管理対象外の`artifacts/`に保存し、レビュー可能な証跡をPRへ添付する。採用判断は`docs/decisions/`のADRに記録する。OS・SDK・schema・呼び出し・プライバシー方針を変更するときは、関連する根拠・検証条件・採用理由を合わせて更新する。
