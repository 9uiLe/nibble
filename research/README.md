# 製品設計の研究資料

対象はiOS 26.0以上のnibble。一次資料の確認日は **2026-09-13**。作業中のスニペット利用と作成・編集・削除を、使いやすく応答の速い体験として設計するための根拠、比較候補、検証条件をまとめる。

## 設計判断と資料の位置づけ

製品の設計は、利用場面、iOSの権限とプロセスの境界、原文の保持、操作・応答性能、保守・復旧の条件を合わせて判断する。資料の推奨は比較候補であり、採用には対象シーンでの試作と検証を必要とする。

実行検証の対象OSは **iOS 26.5のみ**。最低対応OS 26.0への適合はdeployment targetと個別APIのavailabilityで点検する。

開発環境はNix、ローカルのApple CLI、Simulator操作用のsim-use、Ubuntu CIで構成する。[検証基盤の設計](../docs/decisions/0001-local-ios-verification.md) は採用済みの構成を定義し、[ローカル iOS 検証](../docs/ios-verification.md) は操作手順を定義する。

`VerificationApp` は検証コマンドと撮影の成立を確かめるfixture。製品本体のUI、保存・共有方式、呼び出し導線、同期は検証計画の評価対象であり、fixtureの結果を製品の合格判定に使わない。

## 設計上の主要な制約

- **呼び出し・取り込み・挿入は別の能力。** 公開APIによる任意画面への重ね合わせや全入力欄への直接挿入を前提にせず、対象シーンで導線を比較する。[01](01-invocation-and-platform.md)
- **Keyboardの共有領域には読取専用の条件がある。** Apple文書はFull Accessなしの読取を説明するが、選定DBの初期化や更新反映は別途検証が必要。共有DBと読取用snapshotを比較する。[01](01-invocation-and-platform.md)、[02](02-data-and-architecture.md)
- **保存原文と検索表現を分ける。** Unicodeの互換正規化は意味のある区別を失う場合があり、FTS5だけで短い日本語の部分一致を満たせるとは限らない。[02](02-data-and-architecture.md)
- **操作数と完了時間を合わせて評価する。** 探索、誤選択、修正、作業復帰を含むタスクで比べ、実機の基準値から性能予算を決める。[03](03-ux-and-performance.md)
- **APIごとに最低対応OSを確認する。** MetricKitの新APIにはiOS 27以降のものがあり、26.0では互換APIの評価が必要。親frameworkの対応だけでは判断しない。[03](03-ux-and-performance.md)
- **保存・ロック・コピー・同期で保護範囲が変わる。** Data Protectionの既定値は再ロック後の読取を防ぐとは限らず、コピー期限は他アプリに保存済みの内容を回収しない。[01](01-invocation-and-platform.md)、[04](04-security-distribution-and-operations.md)

## 対象範囲と未決定事項

評価の基礎データはテキストとし、保存・検索・コピー・挿入を扱う。plain text / rich text、画像・ファイル、変数展開を含む製品仕様は未決定。同期・アカウント・AI・課金は必要性と運用負担を比較して判断する。

| 領域 | 未決定事項 |
| --- | --- |
| 利用シーン | 製品の入口、対象host、対応する入力形式と成功条件 |
| データ | モデル、データ量、保存・共有方式、検索規則、同期の要否 |
| 操作と表示 | 画面構成、片手利用等の優先度、実測に基づく性能予算 |
| 保護 | 機密スニペットの扱い、公開・収集するデータ、プライバシー宣言 |
| 配布と運用 | 配布・課金・問い合わせ・復旧の方法と担当 |

製品の実験V0〜V8の実施結果は未記録。APIの文書上の仕様、検証基盤の実行結果、製品の動作・性能の検証結果を区別する。

## 根拠の分類

- **事実：** Apple公式API文書、WWDC公開transcript、Swift・SQLite等の一次資料、原著論文に基づく仕様・知見。
- **推奨・設計への示唆：** 事実をnibbleの目的へ適用した案。実装とユーザーテストで評価する。
- **未確認：** 採用SDK、実機、hostアプリ、審査などで確認すべき条件。

各章の資料台帳にURL、著者・発行主体、日付、閲読範囲、適用限界を記載する。Apple DocCは公式JSON本文も参照し、通常の文書URLを引用する。動画のtranscript読解は動画の視聴と区別する。原著の実験値をnibbleの達成性能や普遍的な閾値として扱わない。

外部の論文PDFや文書全文は転載せず、要約・分析・出典・検証条件を保存する。競合製品の二次記事や市場規模の推計は根拠に含めない。

## 採用と更新の手順

1. 対象資料の更新と、使用SDKの型・memberごとのavailability、extension・言語・端末の制約を確認する。
2. [検証計画](05-decisions-and-validation.md) に従い、コミット・端末・OS・データ条件・結果・画面証跡を記録する。
3. 比較結果と採用理由を `docs/decisions/` のADRに記録する。
4. OS・SDK、保存スキーマ、呼び出し導線、プライバシー方針の変更に合わせて資料と検証条件を更新する。

ローカルMacとUbuntu CIの責務、PRの証跡要件は [開発ガイド](../CONTRIBUTING.md) に従う。実行ログ・画像・動画は `artifacts/` に保存し、レビューに必要な証跡を閲覧可能な形でPRへ添付する。
