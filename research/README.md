# nibble の開発に必要な知識

調査日：**2026-09-13**。対象：**iOS 26.0 以上**。開発ルール導入後の `main`（`feefc0e`）を前提とする。

このディレクトリは、nibble の「作業を妨げず呼び出せ、スニペットを簡単に作成・編集・削除・利用できる」という価値を、実装可能な設計にするための調査資料である。技術スタックを決定した ADR や、動作検証の結果ではない。

## 設計に影響する主要な知見

- **呼び出し・取り込み・他アプリへの挿入は別の能力。** iOS の公開 API だけで任意の画面へ重ねて表示したり、全入力欄へ直接挿入したりする前提は置けない。対象シーンで入口を比較する。[01](01-invocation-and-platform.md)
- **Full Access なしの Keyboard にも共有領域の読取という候補がある。** 現行 Apple 文書では読取専用アクセスを説明している。ただし iOS 26.0 での DB 初期化・更新反映は未確認であり、読み取り用 snapshot と比較する。[01](01-invocation-and-platform.md)、[02](02-data-and-architecture.md)
- **保存原文と検索表現を分ける。** Unicode の互換正規化は意味のある区別を失う場合があり、FTS5 の採用だけでは短い日本語の部分一致検索を満たせない。[02](02-data-and-architecture.md)
- **操作数だけで使いやすさを判断しない。** 原著 4 本から操作量、対象の大きさ、遅延と誤りの関係を整理した。nibble では探索・誤選択・修正・作業復帰を含めて評価し、実機の基準値から性能予算を決める。[03](03-ux-and-performance.md)
- **最新資料と最低対応 OS を照合する。** 例えば現行 MetricKit の新 API は iOS 27 以降であり、26.0 では互換 API の評価が必要。framework 全体の対応 OS だけでは採用できない。[03](03-ux-and-performance.md)
- **ロック・コピー・同期で保護範囲が変わる。** 既定の Data Protection は再ロック後もアクセス可能な場合があり、コピー期限は他アプリに保存済みの内容を回収しない。保存場所と露出する入口を組にして設計する。[01](01-invocation-and-platform.md)、[04](04-security-distribution-and-operations.md)

## 調査範囲

主にテキストの保存・検索・コピー・挿入を対象にした。これは調査を具体化するための仮定であり、plain text / rich text、画像・ファイル、変数展開等の製品仕様を確定したものではない。

| 領域 | 調査した内容 | まだ確定しないこと |
| --- | --- | --- |
| 利用シーン | 本体、App Intents / Shortcuts、Controls、Widget、Share / Action、Custom Keyboard、deep link | 初期版に入れる入口、host 別の実際の成功率 |
| データ | 保存方式、プロセス間共有、並行処理、検索と日本語、同期、移行・復元 | 実際のモデル、データ量、採用 DB、同期の要否 |
| 操作と表示 | 操作数、指・タッチ対象、入力、検索、待ち時間、アクセシビリティ | 画面構成、片手利用等の優先度、実測に基づく性能予算 |
| 保護 | 権限、ロック状態、Keychain / Data Protection、ログ・snapshot、Privacy Manifest | 機密スニペットの扱い、収集データ、最終的な宣言内容 |
| 開発と運用 | Swift Testing / XCTest、Nix / Xcode / SwiftPM の境界、TestFlight、App Review、ライセンス | Xcode の採用版、配布・課金・問い合わせの運用 |

同期・アカウント・AI・課金は、将来の設計判断に必要な境界として触れる。初期版の必要機能とはしていない。競合製品の二次記事や市場規模の推計はこの調査の根拠にしていない。

## 根拠の読み方

- **確認した事実：** Apple の公式 API 文書、WWDC の公開 transcript、Swift / SQLite 等の一次資料、原著論文で確認した内容。資料 ID は各ファイル内の台帳に対応する。
- **設計への示唆・推奨：** 上記の知識を nibble に適用した提案。実装・ユーザーテストで検証する。
- **未確認：** 実機、採用 SDK、host アプリ、審査などでしか確定できない点。資料の存在だけで確認済みにはしない。

資料台帳には URL、著者・発行主体、分かる範囲の年・更新日、実際に読めた範囲を記載した。Apple の DocC は公式 JSON 本文も使用し、通常の文書 URL を引用した。動画は transcript の読解を明示し、動画を視聴したとは扱わない。古い archive は現行資料と照合し、論文の実験条件と現代の iPhone への適用限界を区別する。

**最新ページにある API が iOS 26.0 で使えるとは限らない。** framework の対応 OS、個々の型・member の availability、実行する端末・言語・extension の制約は別々に確認する。原著の実験値も、nibble の達成済み性能や普遍的な閾値には置き換えない。

外部の論文 PDF や公式文書の全文はこのリポジトリに転載していない。ここには要約・分析・出典・検証課題を保存する。

## 更新と意思決定

1. 技術の採用前に、該当資料の更新と使用する SDK の availability を再確認する。
2. [検証計画](05-decisions-and-validation.md) の小さな検証を実施し、対象コミット・端末・OS・データ条件・結果・画面証跡を残す。
3. 選択肢の比較と採用理由を `docs/decisions/` の ADR に記録する。調査資料の推奨だけを採用決定にしない。
4. OS / SDK・保存スキーマ・呼び出し導線・プライバシー方針を変更するとき、該当章と検証結果を更新する。

ローカル Mac と Ubuntu CI の責務、PR の証跡要件は [開発ガイド](../CONTRIBUTING.md) を引き続き適用する。
